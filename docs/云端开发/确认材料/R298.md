来由: R297 第 1 轮审核意见 04. audit_trail 原来只有主键索引, 工作台时间线的最近一页与游标翻页每次都要取出本项目的全部留痕再排序.

第 1 轮不通过 (blocker 1, minor 2, nit 1), 四条都在 fix 提交里改了; 按协调者指示不再送审, 由协调者在新库上核对.

## 改动摘要

- `persistence/models.py` 声明三个索引:
  - `TRAIL_BY_TIME` (engagement_id, created_at, id): 时间线的最近一页与游标往前翻, 带或不带一组 kind;
  - `TRAIL_BY_KIND` (engagement_id, kind, created_at, id): 只取一类的 all_of_kind 与 last_of;
  - `TRAIL_BY_KEY` (engagement_id, idempotency_key) WHERE idempotency_key IS NOT NULL: find_success.
- 迁移 0015 用这三个 Index 对象 `create(checkfirst=True)`, 降级倒序 DROP INDEX IF EXISTS.
- 接口文档第 4, 9 节同步.
- 连库用例: `test_trail_reads_use_the_indexes` (7 种读法, 截下真实 SQL), `test_migration_0015_round_trip`.

## 方案取舍

- 含 kind 的索引: 加. 只取一类的读法在数据概览轮询 (每 3 秒), 复核, 延后与对话记忆里都有, 只靠时间索引要扫过本项目的全部留痕.
- 防重复键的部分索引: 协调者补充指示并进本条. 一个键至多几条, 不把排序键放进去; find_success 那一例不关排序.
- 时间线带的五类是 IN 一组, 归时间索引: 倒着扫取够一页即停, 比按类型分段取再合并排序省.

## 验收对照

1. 有 (engagement_id, created_at, id) 的索引 ix_audit_trail_engagement_time; 另有含 kind 的与防重复键的两个.
2. 七种读法 EXPLAIN 都用到目标索引, Index Cond 含 engagement_id; newest, before, 带时间线五类的两种, 按类型一页, last_of 计划里没有 Sort.
3. 迁移: 属主的回滚事务里降级后三个索引都没了, 升级两次后 pg_indexes 的定义与预期一致 (含部分索引的 WHERE); 在空库与有数据的旧库上都升级通过 (见下).
