来由: Issue #51 验收 3. 规模 M, 档位 xhigh. 分支 yi-r340, 基于开发分支 84d8f1d (含已合入的 R339, R342, R324 与 R329; 在 R342 修正 a84a076 上开发, 先后变基到 1a1a3dd, f56e972 与 84d8f1d, 都无冲突; 严审后的修正另作一个提交). 不需迁移.

## 改动摘要

- `prompts/_output_language.md.j2` (新): 共用的 "## Output language" 一节, 两个宏: `narrative_language()` (写文字的程序) 与 `extraction_language(explained)` (抽取类, 参数为用工作语言写的说明性字段). 语言取变量 output_language.
- 17 个程序提示词在末尾引入: 11 个写文字的, 6 个抽取类 (DOC-CLASSIFY 与 DOC-SHEET 的 reason 为说明性字段, 其余没有). PLN-15 原来的 "Australian English" 一句并进这一节. RPT-03 不动 (归 R341).
- `judgment_engine.call_llm`: 渲染变量加 output_language, 取 run.language. 上传即处理的执行在 R339 修正 (07) 已带项目语言; 其余调用方给的都是 build_run 建的执行记录 (GEN-09 用被复核的那次).
- 前端 (范围里 R339 普审 08 那一项): 判断 (判断卡, 争议两方, 复核意见, 复核队列并排视图, 程序详情), 计划 (叙述, 时间表, 质量复核与专家评估, 程序说明) 与报告正文的 lang 属性, 由写死的 en 改为执行记录的语言 (`lib/working-language.contentLanguage`, `useContentLanguage`). 没有 run_id 的报告稿为 en.
- 接口文档第 5 节 (call_llm 的渲染; 语义级不按语言判断) 与第 8.2 节 (提示词的输出语言).
- 测试: `tests/test_prompts_language.py` (新), test_output_validator.py (中文正文), 前端 tests/working-language.test.ts.

## 方案取舍

- **共用片段用宏:** 用 `import ... with context` 引入, 写文字与抽取是同一文件的两个宏. output_language 只在片段里出现, 所以各模板的头注释不变, "头注释变量 = 模板用到的变量" 那几条守卫 (PLN-15, FIN-03, FIN-09) 也不受影响. 片段里缺省为 en, 现有直接渲染模板的用例 (不给这个变量) 不用改; 真实调用一律由 call_llm 注入.
- **只在 call_llm 一处注入:** 取 run.language, 不读项目. 调用方不用各自传, 调用方给的同名变量也被覆盖. 重跑是新的执行记录, 语言取建它时项目的值 (R339).
- **en 也有这一节:** 两种语言同一套规则, 只差语言名, 所以英文提示词也多了这一节. mock 的 fixture_key 与输出都不变.
- **抽取类:** 说明性字段逐个登记. ACC-08-extract 的 good_faith_reason 是决议里写明的理由, 算抽出的值.
- **守卫怎么渲染:** 每个模板只给 output_language, 其余变量取占位 (ChainableUndefined 加比较与运算), 只为走到末尾那一节; 模板正文按头注释变量的渲染另有 test_knowledge 的用例. 新模板缺这一节时失败. RPT-03 列在 LATER (归 R341), 加上这一节后那条用例会提示把它去掉.
- **日期与金额:** 写法照各模板原有的规则, 如 PLN-15 的 "1 July 2025". 对外文件的写法归 R341.
- **前端 lang 的已知差距:** R341 合入前, 中文项目的报告正文仍是英文; R343 合入前, mock 下中文项目的判断也仍是英文. 这两种情况下 lang 都随执行记录的 zh, 与 R339 的生成语言标注同一口径.

## 语义校验里按英文词判断的地方 (逐条)

1. `report_checks`: ReportDraft 两段首行须为 REPORT_HEADINGS 的英文标题. 归 R341, 本条不动; RPT-03 也不引入输出语言一节, 报告照旧用英文写.
2. 其余校验都不按英文词判断, 不改. 逐个看过的有: chain_semantics, judgment_semantics, nature_semantics, judgment_ref_errors, going_concern_semantics (片段 ID), verification_semantics, plan_checks (段名是 JSON 键, 另查程序 ID, 日期, 依据非空), 独立复核, 抽取的引用级, 回函的语义级, 以及 llm_outputs 里的模型校验. 它们只核对类型, 指针, ID, 枚举, 金额, 日期, 键与非空.
3. 依赖固定写法 (不是英文词) 的, 靠提示词保住, 不改代码: locator 须为字段名 (REGISTRY_POINTED, accrued_interest_cents, 客户画像的字段), 回函账号须与账户相同, 计划 sections 的键. 输出语言一节写明 JSON 键, 枚举, ID 与指针字段照规定, 抽出的值照原文 (模板规则要求的格式除外); 提示词正文里引号给出的固定值照抄 (审核 R340-01, 两个宏都有这一句). 逐条: CSH-02 的 `account` "Cash", "Interest income", "Interest expense" 与 REV-02 的 `account` "Revenue" 是提示词给的字面科目名, 不在输入里, 靠 "引号固定值照抄" 保住; DOC-SHEET 的空表头列名 `Column n` 是套用方案时按名对应的生成名, 靠抽取宏 "规则要求的格式除外" 写明照规则写; FIN-03, FIN-09, GEN-09 的 `account` 另写明 "as it appears in the inputs".
4. 下游按文字对应的两处, 不改代码: `workpaper.misstatement_objective` 按审计目标的科目名在错报科目里找整词, 靠上一条的字面科目名照抄与 "科目名照输入" 保住; `fieldwork` (GEN-03 关联方, 第 389 行一带) 按合同对方名配关系图上的公司, 靠抽取宏的 "照原文" (DOC-04 的 counterparty 照原文抽出) 保住.

## 验收对照

1. `test_every_prompt_states_the_output_language` (18 个模板 × zh, en): 截出末尾一节, 核对工作语言, 只出现一种语言名, 并按关键词核对口径 (写文字的程序: 文字字段用工作语言, 引文放在引号里照原文, 名称, 科目名与准则原文照输入; 抽取类: 值照原文, 只有登记的说明性字段用工作语言). RPT-03 断言没有这一节.
2. `test_chinese_text_with_english_quotes_passes_four_levels`: REV-03 CON-002, CSH-02 BA-01 与 GEN-02 XJ-405 (Xero, external) 各改出一份中文版, 引号里是合同或回函的英文原文; 中文版与原英文版都一次通过四级, 中文正文原样留在输出里.
3. `test_extracted_values_do_not_depend_on_the_language`: DOC-CLASSIFY, DOC-04, DOC-06, DOC-REGISTRY, DOC-SHEET 经真实代码路径各抽一次, 同一份 mock 输出在 zh 与 en 下结果相同且都通过校验, 两次提示词只差末尾一节. 项目存储里的项目是 en, 提示词仍随执行语言变, 说明没有读项目. ACC-08 的抽取还没接进程序, 只有守卫覆盖.
4. 上一条同时断言 fixture_key 相同. Numbat 与 Xero 的现有用例一个没改, 全部照过.

变异核对 (都被上面的用例杀掉): 删去一个模板的这一节; 抽取类误用写文字的宏; 新加一个没有这一节的模板; call_llm 不注入; 语义级加一条 "结论须为 ASCII". 前端的 contentLanguage 有 bun 用例.

## 审核结论

第 1 轮严审没通过 (1 major, 3 minor, 2 nit), 在修正提交里改:
- 01 (major) 两个宏都加一句 "提示词正文里引号给出的字段固定值照抄, 不翻译", 守卫的两组关键词补上; FIN-03, FIN-09, GEN-09 的 `account` 写明照输入; 新用例 `test_literal_account_names_stay_as_given` (zh 的 CSH-02, REV-02 提示词里字面科目名原样在, 这一句在); 上面第 3, 4 条逐条列出.
- 02 抽取宏改为 "exactly as written ... apart from the formatting the rules above require (amounts, dates, digits-only numbers, name order, generated column names such as `Column n`, one-sentence summaries)"; 末尾加的 "one-sentence summaries" 是为 ACC-08-extract 的 good_faith_reason. en 的 mock 输出与 fixture_key 不变 (抽取用例照过).
- 03 守卫从 "explanatory field" 那一行取全部反引号字段名, 与登记的整个相等 (个数与顺序).
- 04 FIN-08 材料每条错报加 source_run_id (来源判断的执行), 接口文档与 lib/misstatements.ts 同步, 页面的来源结论改用 useContentLanguage; generate-client 无差异 (材料是 JSON).
- 05 test_llm_call 的 test_request_fields 加一条断言: zh 执行, 变量带 output_language en, 提示词仍为 Simplified Chinese.
- 06 default("en") 照旧.
