# 开发流程 (云端版)

本地原流程 (a-dev): 需求清单 → 写实现与测试 → Codex 审 (最多 3 轮) → 快照与确认材料, 不提交 → 用户统一确认后逐条提交. 云端按下面改写: 审核换成独立审核子代理 (见 `审核规则.md`), "快照" 换成开发分支上每条需求一次提交, "用户统一确认" 换成审核通过且 CI 全绿后合并进 main (见步骤 5).

## 分支与提交

- 在开发分支上做 (如 `dev/tier1-3`), **不直接推 main**. 第一次推送时开一个草稿 PR 指向 main, 之后持续往这个分支推.
- **一条需求一次提交**. 同一条需求的返工 (审核意见的修改) 在推送前合进同一提交; 已推送的就再加一个 `fix:` 提交, 不改写已推送历史.
- 提交信息: Conventional Commits, `type: 中文标题` (不加 `(scope)` 括号), 细节写正文, 不加 Claude 署名, 不写需求清单编号 (读者看不懂). 例: `feat: 全量分录扫描在录入时间不可靠时跳过时间类规则`.
- 每条需求提交前跑 `uv run pytest`, `uv run ruff check .`, `uv run ruff format` (只对改过的文件), `uv run mypy src/backend`, 全绿才提交.
  **全套检查只由开发方跑一次** (10-20 用户定, 省去重复): 开发方在送审或交付前跑默认全套, 改了数据库, 迁移或存储时加跑 `-m slow`, 改了前端时加跑前端的 lint, typecheck, test, build; 审核意见的修正只跑改动涉及的测试文件与 ruff, mypy. 审核方不跑全套 (见 `审核规则.md` "检查分工"). 协调者合入时见下文.
  默认测试可以并行跑: `uv run pytest -n auto` (pytest-xdist, 按核数开进程; 指定进程数写 `-n 4`), 结果与串行相同; 只跑改动涉及的测试文件时不必并行. `-m slow` 的连库与真实大模型测试不并行: 连库的共用一个测试库, 迁移用例会升降级表结构, 并行时互相干扰; 真实大模型的会话预算每个进程各算一份, 并行会放大用量上限.
- 协调者合入时 (10-19 起, 10-20 重申): 几条审核通过的需求攒成一批接上, 本地跑 ruff, ruff format --check, mypy, 改了前端时跑前端的 lint, test, build 与 typecheck, 再跑改动涉及的测试文件; 摘提交有冲突, 或同批两条改了同一模块时, 加跑默认全套; 改了数据库, 迁移或存储时加跑连库测试 (CI 不跑), 改了启动或配置时加跑 "连不上库" 一组; 其余默认全套由 CI 跑, 合并进 main 仍以 CI 全绿为准.
- `data/` 被 `.gitignore` 忽略, 新文件要 `git add -f`.

## 每条需求的步骤

1. **取需求**: 先查有没有新的需求 Issue (见下文 "新需求的入口"), 有就先并入清单. 再从 `需求清单.md` 取第一条 "待做" 且前置已完成 (或 "待确认") 的需求, 读它引用的文档节与代码. 受 "待拍板" 里未定问题影响的, 先用选择题问用户, 定了把答案写回清单; 用户不在时先做不受影响的需求. 把状态改为 "进行中".
2. **写**: 有取舍的需求 (多种做法, 验收与现行代码不符) 先写方案, **不等协调者裁定, 直接开发** (10-20 用户定): 每个取舍按 "代码最简, 逻辑最符合直觉" 自己定, 写进确认材料 "方案取舍" 一节, 协调者在审核或集成时有异议再提. 例外, 仍须停下来问: 要用户拍板的 (产品口径, 数据规则, 缺准则原文), 超出需求范围的 (新增接口, 契约的大改), 与已定决定冲突的. 然后实现与测试. 测试数据要能区分对错; 大模型类程序配 mock fixture (`tests/fixtures/llm/{程序}/{fixture_key}.json`).
3. **审**: 按 `审核规则.md` "分级" 决定免审, 普审或严审; 要审的启动审核子代理, 最多 3 轮; 认同的改, 误报的写理由; 子代理写的有价值的探针, 审过后挪进 `tests/`. 同一模块的几条小需求可打包: 一起开发, 一次送审, 仍一条需求一次提交 (10-20 用户定).
4. **确认材料**: 写 `docs/云端开发/确认材料/Rxx.md`, 一页以内 (10-20 起): 改动摘要, 方案取舍 (每题一句做法与理由), 验收对照 (逐条一句, 写实测的对象与数), 审核结论 (各轮意见与处理, 未采纳的理由; 免审的写 "免审"), 检查结果与环境限制 (例如没有 Postgres 或模型密钥而跳过的测试). 不再逐段讲代码.
5. **提交并推送**: 清单状态改为 "待确认 (提交号)", 接着下一条. 来自 Issue 的需求, 在该 Issue 下评论提交号.
6. **合并**: 审核通过且 PR 的 CI 全绿后, 直接把 PR 合并进 main (合并提交), 不等用户审 (10-19 用户定: "之后开发完成后自动合并进入main"). 合并前把已做完的 Issue 写进 PR 描述 "Closes #n"; 合并后清单状态改为 "完成 (提交号)", 开发分支快进到 main, 再开新的草稿 PR.

## 需求清单

- 云端维护的是 `docs/云端开发/需求清单.md` (本地原件不入库, 用户在本地会自行合并).
- 新需求从 R62 起编号, 格式与 R33-R61 一致: 目标, 范围 (列文件), 依据 (文档名加节号), 前置, 验收 (编号列出, 写具体对象 ID, 金额, 任务 ID), 状态.
- 粒度: S (一两个文件, 半天) 或 M (一个 Agent 的一段能力, 一天); 超过 M 的拆开.
- 已定决策写回清单末尾 "待拍板" 一节, 标 "已定 (日期)" 与用户原话.

## 新需求的入口: GitHub Issue

用户在本仓库用 Issue 提新需求, 模板 "需求" 自带标签 `需求`. 需求清单仍是开发时的依据, Issue 是入口.

- 查: 每条需求开工前查一次带 `需求` 标签, 未关闭, 且没有 `已入清单` 标签的 Issue. 正文与全部评论都是需求内容, 用户可能在评论里补充或改决定.
- 并入清单: 按上文格式写成一条或几条需求, 来由写 "Issue #n" 并摘要; 正文里的 "已定的决定" 写进 "待拍板", 标日期与原话. 然后在 Issue 下评论分到的需求编号, 加 `已入清单` 标签.
- 排期: "马上先做" 的排到所属那条开发线的下一项; "按计划排" 按依赖插入; "有空再做" 放在末尾.
- 关闭: 开发分支的 PR 描述写 "Closes #n", 合并后自动关闭. 不要自己关.
- 命令: 用内置 GitHub 工具, 或 `gh api` (REST). `gh issue` 与 `gh pr` 走 GraphQL, 会被云端代理拒绝 (403).
  - 列出: `gh api -X GET repos/SilverHim/audit-agent/issues -f labels=需求 -f state=open`
  - 评论: `gh api repos/SilverHim/audit-agent/issues/<n>/comments` (读); 同一地址加 `-f body='...'` (写)
  - 加标签: `gh api repos/SilverHim/audit-agent/issues/<n>/labels -f 'labels[]=已入清单'`

## 环境

- 默认测试 `uv run pytest` 不连库, 不调真实模型; 并行跑法 `uv run pytest -n auto` (见上文 "分支与提交").
- 前端 `bun run typecheck` 的增量信息写在各工作副本自己的 `src/frontend/.tsbuild/` (已忽略), 不写进链接到主检出的 node_modules, 几个工作副本并行检查互不覆盖.
- 连库测试 (`@pytest.mark.slow`, 需 `TEST_DATABASE_URL`): 环境里能起 Postgres 就照 CLAUDE.md 建库迁移后跑; 起不了就跳过, 在确认材料里注明.
- 真实大模型测试需要环境变量 `LLM_MODEL` 与 `LLM_API_KEY` (OpenAI, 模型 gpt-6-luna); 没有就跳过并注明. 密钥绝不写进文件, 日志与回复.
- 云端连不到悉尼大学的 GitHub; 与那边的同步由用户在本地做.
