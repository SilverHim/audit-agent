来由: Issue #47 验收 3 的后端 (第 14 批取舍 4). 父提交为 R206 (jia-r206); 规模 M, 档位 high.

## 改动摘要

- `contracts/views.py`: PlanView (current_plan_id, plans, decisions, objectives, risks, rows), PlanRow (objective_id, procedure_id, extent, sample_size), PlanExtent.
- `orchestration/query.py`:
  - 纯函数 `plan_view(values)`, `plan_rows`, `plan_row`.
  - `GraphStateQuery.plan(eid)` 读检查点状态, 不查 Store.
- `api/routes/engagements.py`: `GET /engagements/{eid}/plan`, 函数名 get_plan, operation_id engagements-get_plan.
- 前端: 重跑 generate-client. openapi.json 只多了这个接口与两个模型, 原有 operation_id 都没变.
- 测试:
  - test_query 加 2 例: 纯函数的行序, 范围与各列表; 基线项目经 HTTP 取, 不存在的项目 404.
  - test_decisions 加 `test_plan_page_at_gate` (共用 plan_gate 的那次运行); R206 走通用例末尾补 GET /plan 的断言.
  - 经 HTTP 取的都与 StateQuery.plan 的结果比对.
- 文档: 接口文档第 7 节 (StateQuery 协议, 视图模型与范围的取法), 第 10 节接口表.

## 方案取舍

- 只读检查点状态: 与 GET /gate 同一来源. 决定提交后, Store 会先于检查点更新, 这段时间计划页可能晚一拍; 后台推进后即一致, 与总览的闸门显示相同.
- decisions 列全部 PLN-15 决定 (含信息不足): 修订历史要看到每次决定. 前端按 decision 区分驳回理由与批准.
- 程序表的行不在状态里的目标 (正常流程不会有) 排在已知目标之后, 按 ID; 不报错, 页面照常显示.
- 范围的判断按清单写 (params 里有整数 sample_size 为抽样); 布尔值不算整数, 免得 True 被当成 1.
- Xero 的验收放在 test_decisions: 那里已有停在闸门的共用运行和驳回再批准的运行, 不另跑.
