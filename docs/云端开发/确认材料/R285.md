# R285 确认材料: 工作区时间线的 key 改用留痕 ID

来由: R281 审核与甲复看时, 工作区页面的控制台报 React 重复 key (如 decision::, completed::). 协调者核实了原因: 时间线条目的 key 由类型, 时间与 id 拼成, 没有 id 且时间相同 (或为空) 的条目会撞号.

## 审核结论

规模 S. 协调者定为改完不另审.

## 改动摘要

- `src/frontend/src/lib/timeline.ts`:
  - 时间线条目加 `key` 字段. 类型写成 `TimelineItem = TimelineEvent & { key: string }`, 各类条目的其他字段不变.
  - key 取条目来源留痕的 ID (TrailEntryView.id, 后端写入时生成, 真实库为 TR-{uuid4}).
  - 相邻合并的 "程序完成" 取这一组第一条留痕的 ID. "项目创建" 只有一条, key 固定为 created.
  - 留痕缺 ID 时 (接口允许为空), 退回它在按时间排序后的序号 `#{序号}`. 序号的形式不会与留痕 ID 撞号.
- `src/frontend/src/routes/engagements/$eid/index.tsx`: 时间线列表用 `key={item.key}`, 不再用类型, 时间与 id 拼 key.
- 只改前端, 后端契约与生成的客户端不变.

## 讲解

- 撞号有两种情形:
  - 留痕时间为空. 假留痕 (tests/fakes.FakeTrail) 只发 ID, 不填 created_at. 这时 key 成了 `decision::`, `completed::` 与 `phase::`.
  - 时间相同. 真实实现 (services/audit_trail.py) 的 created_at 取写入时刻, 精确到微秒, 相同的情形少见, 但不能排除 (调用方也可以自带 created_at). 审核时看到的警告来自第一种情形 (page.route 加假后端).
- 原来只有问答与数据管理两类条目带 id, 决定, 阶段变化, 程序完成与稍后处理都没有.
- 留痕 ID 每条唯一, 刷新后不变 (后端按 ID 存取), 所以 key 既唯一又稳定.
- 一条留痕至多归入一个时间线条目 (合并的程序完成也只占用组内第一条的 ID), 条目之间不会共用 ID.
