## 首次准备

```bash
git clone https://github.sydney.edu.au/ELEC5620-Wed-14-16-Group-16/ELEC5620-demo.git
cd ELEC5620-demo
cp .env.example .env
uv sync
uv run pre-commit install --hook-type pre-commit --hook-type pre-push
cd src/frontend && bun install
```

## 提交与推送

直接推 main，不开分支，不强制代码审查。

1. 开工前 `git pull --rebase`。
2. 一次提交只做一件事；还没推送的修订用 `git commit --amend` 合进上一次提交。
3. 提交信息用 Conventional Commits：`<type>(<scope>): <标题>`。type 取 feat（新功能）、fix（修复）、docs（文档）、refactor（重构）、test（测试）、chore（杂项）、build、ci；scope 取模块名，可省略；标题一句话写结果，细节写在空一行后的正文。例如 `feat(persistence): 实现 AuditOutputStore.put`、`docs: 更新开发接口文档第 7 节`。
4. 推送前再 `git pull --rebase`，钩子全部通过才推。
5. 不用 `git push --force`；推错了用 `git revert`。
6. 不提交跑不起来的代码：没写完的功能用 `NotImplementedError` 占位，保证 main 随时能启动。

## 分工边界

- 每个文件由谁实现，以 [开发接口文档.md](开发接口文档.md) 第 1 节和 [Demo需求文档.md](Demo需求文档.md) 第 5 节为准。改别人负责的文件，先在群里说。
- 改 `src/backend/contracts/` 或开发接口文档：推送前在群里告知另外两人，并在同一次提交里同步改接口文档。
- 程序 YAML 中规则的 `sql` 由 B 写，其余字段与 prompt 由 A 写。
- 实现与文档不一致时，先在群里确认，再在同一次提交里改文档和代码。

## 代码检查

| 范围 | 检查 | 时机 |
|---|---|---|
| Python | `ruff check`、`ruff format` | pre-commit |
| Python | `mypy src/backend`（启用 pydantic 插件） | pre-commit |
| Python | `pytest -m "not slow"` | pre-push |
| 前端 | `biome check`、`tsc -b` | pre-commit |

- 连数据库或调真实 LLM 的测试标 `@pytest.mark.slow`，平时手动跑。
- 测试一律用 `LLM_MODE=mock`，fixture 放 `tests/fixtures/llm/`。

钩子配置在 `.pre-commit-config.yaml`。

## Actions 试跑

GHE 已开启 Actions，但能否用取决于学校是否提供 runner。工作流在 `.github/workflows/ci.yml`，跑的检查与本地钩子相同。

推送后出现以下任一情况，就删掉这个工作流，只靠本地钩子：
- 10 分钟后任务仍是 Queued，说明没有 runner。
- `actions/checkout` 报找不到，说明实例没有同步官方 actions。

能跑通的话，谁推送导致失败，谁当天修。
