## 3. 用户定下的工作规则 (必须遵守)

- 选代码最优雅, 最简洁, 逻辑最符合直觉的做法, 哪怕要重做; 不让项目变成屎山. 测试文件也一样: 不写依赖源码文本的断言, 不重复造辅助函数, 不为过测试放宽断言.
- 需要拍板的按推荐项定, 写进需求清单 "已按推荐定" 或对应 Q 节, 用户可推翻. 只有产品口径, 数据规则, 缺准则原文这类才停下来问; 问用户一律用白话选择题, 推荐项在前并给正反.
- 一律简审 (Q33): 读增量, 跑本条相关的检查, 没有必改的问题 (测试假通过, 结果错, CI 红, 明显难维护) 就合入.
- 一条需求一个提交 (Conventional Commits, `type: 中文标题`, 正文几行要点); 不写确认材料; 审核修补并进原提交后再合入; 不 force push 已推送的分支.
- 状态更新与代码一起推, 别为改两个字单独推一次 (每次推送都跑一轮 CI).
- 开发完成, CI 全绿后自动合并进 `main` (合并提交), PR 描述写 `Closes #n`; 合并后清单状态改为 "完成 (合并提交号)", 开发分支快进到 `main`, 再开新的草稿 PR. 来自 Issue 的需求在 Issue 下评论分到的编号与提交号, 并加 `已入清单` 标签.
- 只有用户问时才汇报进度; 回复用户用中文.
- 改 `contracts/` 时同一提交改 `docs/开发接口文档.md`; `src/frontend/src/client/` 与 `routeTree.gen.ts` 是生成文件, 用 `bun run generate-client` 生成, 不手改, 冲突时重新生成.
- Python 注释与 docstring 写中文, 半角标点.
