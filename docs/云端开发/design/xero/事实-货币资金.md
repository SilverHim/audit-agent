# 货币资金: 事实与补造设计 (Xero Demo Company (AU), 期间 2026-07-01 至 2026-09-30)

结论: 090 和 091 在 09-30 的账面余额与模拟对账单完全一致, 期末没有任何未达账项。所以用真实数据跑, CSH-05 是 0 命中, CSH-02 两户都是 agreed, 也不会产生 Judgment。要让 CSH-02 出现差额, 只能往 Xero 数据或对账单里加合成内容 (见第 4 节第 1 项)。真实存在的现金问题有三个:
- 090 整个季度都在透支。
- 期初转换余额 19,212.21 记在了本期, 挂在 840。
- 透支在 Xero 里按负资产列报。

这三点交给持续经营, 期初余额, 错报分类各组处理。

探查脚本都在 `/private/tmp/claude-501/xero_cash_probe/`, 用系统 python3 (openpyxl) 运行, 以 `python3 -I 脚本名` 执行:
- `common.py`: 公共解析。识别作废对, 金额转成整数分。
- `c1_balances.py` 到 `c9_cashflow.py`: 各项统计。
- `txt/`: 用 pdftotext 抽出的准则原文。

全部数据源与口径:
- 日记账: `raw/journal_report.xlsx`, 368 笔。
- 对账单: `api/20261017-mock/bank_statements.json`。
- 模拟分录: `api/20261017-mock/journals.json`。
- 试算表: API 的 0630 表与 1130 表。
- 金额: 银行科目本身不涉及 GST。下文的余额都是记账金额 (借正贷负), 单位元。

### 1.1 载入后的对象 (按载入器 `map_bank_accounts` 与 `map_bank_transactions` 推出)

| 对象 ID | bank_name (载入器取值) | bsb | account_no | gl_account_code | 来源 |
|---|---|---|---|---|---|
| BA-090 | Business Bank Account (这是科目名, 不是银行名) | 306234 | 12345678 | 090 | accounts.json BankAccountNumber `30623412345678` |
| BA-091 | Business Savings Account | 306234 | 12345679 | 091 | `30623412345679` |

- 两个账户的 BSB 相同, 都是 306234。也就是说, 按结构化字段看, 两户在同一家银行, 同一个分行。
- 流水 ID 的格式是 `BT-{科目}-{4 位序号}`。载入器按 postedDate 排序, 同一天的行保持导出顺序。序号从对账单起始日 07-01 起算, 起始日变了序号就会变。
- 分录行 ID 的格式是 `XJ-{JournalNumber}-{n}`。n 是该笔分录中非零金额行的顺序号。JournalNumber 等于日记账报表的 Journal ID。

## 4 需要用户拍板的事项

**1. 银行回函余额要不要人为设计一笔差额?**

真实数据在 09-30 账实完全相符, 不存在可以直接用的在途款项。

| 选项 | 好处 | 坏处 |
|---|---|---|
| A. 不设计, 回函余额等于对账单等于账面 (推荐) | 和 Xero 真实数据零冲突; 作为求职作品也说得清 | 演示公司的 CSH-02 不会出现 AI 判断与人工复核。这条路径只能由 Numbat 回归测试覆盖, 演示视频里 CSH-02 是空跑 |
| B. 合成一笔银行扣款: 在 090 对账单 10-01 补一行透支利息 -180.20 (起息日 09-30), 银行回函余额 -11,080.64。金额由 c6 按真实日终透支余额乘 10% 年利率除以 365 算出 | CSH-02 能产生 D01 差额 -180.20 与一次判断, 金额有真实依据; CSH-05 仍然相符, 正好体现 "外部函证发现了客户导入的对账单没有反映的内容" | 改了模拟对账单, 之后的流水序号和余额都要后移; 预期结论有歧义: LLM 可能给 misstatement (少记利息费用, 金额 18,020 分), 也可能给 more_evidence; 金额很可能低于实际执行重要性, 触发不了动态降级 |
| C. 把一笔真实的 10 月收款在账面上提前到 09-30, 造一笔在途存款 | 最像教科书里的例子 | 要改 Xero 账面, 会破坏与 API 试算表的勾稽, 不推荐 |

**2. 回函里 090 的透支怎么写?**

| 选项 | 好处 | 坏处 |
|---|---|---|
| a. 有额度 15,000, 即期偿还, 董事个人担保, 无抵销安排 (推荐) | 符合 "连续透支只收月费" 的样子; 给持续经营组提供余量数据 (09-30 剩 4,099.56, 最高用到 89%); 给关联方组提供一项担保事实; 给分类错报提供依据 | 合成条款较多; 担保人名字要和股权组统一; Xero 对账单整季没有利息扣款, 回函只能写 "应计利息 nil", 略不真实 |
| b. 没有额度, 属于未经安排的透支 | 持续经营迹象更重 | 银行一般不会容忍未经安排的透支长达三个月以上, 可信度低 |
| c. 不提额度 | 最省事 | 银行回函通常会列出授信; 持续经营组拿不到余量数据 |

**3. 开户行名称与 BSB 怎么定?**

| 选项 | 好处 | 坏处 |
|---|---|---|
| a. 两户同一家虚构银行, BSB 与账号沿用 Xero (推荐) | 载入器只需要补开户行名; 090 的回函第 3 节可以列出 091, 交叉核对账户完整性 | 对账单里 "NAB" 一类付款方字符串和回函上的银行名不一致, 要在合成说明里注明 |
| b. 两家虚构银行, 091 沿用 Xero 自带的 "Business Savings Bank" | 091 与 Xero 字符串一致 | 091 的 BSB 要另造并覆盖; 两户共用 306-234 本身也矛盾 |
| c. 090 用真实的 National Australia Bank | 与 Xero 字符串最一致 | 等于以真实银行的名义伪造回函, 不推荐 |

**4. 数据集期间改为 09-30 时, 对账单取到哪天?**

| 选项 | 好处 | 坏处 |

| a. 仍取到 10-17 (推荐) | 保留期后 70 行银行流水; CSH-02 的 D02 窗口与期后事项程序都要用 | 要么只改 dataset.json 不重新拉取, 要么让拉取时对账单截止日不受期间限制 |

## 5 风险与不确定

1. **缺 09-30 试算表**: 载入器按 `trial_balance_{period.end}.json` 读本期试算表, 快照里没有 `trial_balance_2026-09-30.json`, 会抛 FileNotFoundError。需要重新拉取一份, 或按 c3 推导 (26 个科目, 借贷合计 0)。CSH-05 与 CSH-02 都用这张表, 不用 gl_balance。
2. **开户行名来源**: 载入器把 bank_name 设为科目名 ("Business Bank Account")。函证请求, Confirmation 的 confirming_party 和留痕摘要都会显示这个名字。合成银行名需要一个覆盖来源, 待载入器确认。
3. **回函目录**: `main.py` 的 MockConfirmationChannel 固定从 `data/demo/confirmations/{account_no}.pdf` 找回函。Xero 账户的回函在那里找不到, A5 存档时会抛 "没有回函", CSH-04 失败。需要按数据集区分目录, 待载入器确认。合成文件放在哪里, 是否进 git, 也待定 (`data/*` 目前被忽略)。
4. **重新拉取的影响**: 用 pull 按 09-30 重新拉取, `_statements` 只取到期末, 期后流水会消失, 见第 4 节第 4 项。另外流水 ID 依赖对账单起始日与导出顺序, 换快照会变号。
5. **透支的符号**: 回函要写明 "overdrawn"。DOC-06 的提示要求透支取负数, 但 "(debit)" 是银行视角, LLM 容易抽成正数 1090044。如果抽错, 会被当成差额 21,800.88 进入 CSH-02。
6. **字符串与合成内容冲突**: Xero 里 "NAB" 等字符串与虚构银行名冲突。另外真实对账单整季透支却没有利息扣款, 任何利息条款都会与它矛盾, 方案 A 只能写 "nil"。
7. **待核项**: 本地无法核实以下几点, 都标为待核:
   - 合成银行名是否与真实机构重名。
   - ABN 82 938 074 116 是否已被登记。
   - Xero 的 ABN 11 111 111 138 是否已被登记。
   - BSB 前缀 306 的真实归属。
   - 对金融机构付款抵扣 GST 是否合规。
8. **AASB 1060**: 本地只有摘要, 相关段号一律待正本。透支能否与现金抵销, 依据的是 AASB 132 与 AASB 101 原文 (已核); 第 2 层是否有不同列报要求, 待正本。
9. **风险清单模板**: 通用模板的现金风险只有 Existence。对 090 来说, 真正的风险是完整性与分类, 而现有程序的触发条件只认 Existence。改风险等级规则不在本次范围内, 只记录这一点。
10. **快照会变**: Demo 每 28 天重置。上面的金额都绑定在 2026-10-17 这份快照上。fixture 的期望值要么由转换器从数据算出, 要么锁定快照的 sha256。
