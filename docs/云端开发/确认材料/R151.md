## 讲解

### 状态 (验收 1)

ProcedureStatus.in_dispute 由 R89 加好 (contracts/models.py, 检查点白名单自动登记). `test_procedure_in_dispute_survives_store_json_and_checkpoint`: 争议中的程序经 JSON (审计产出的存法) 与检查点序列化读回, status 仍是枚举 in_dispute.

### 汇合 (验收 2, `tests/test_collab.py::test_dispute_makes_program_in_dispute_and_listed_first`)

Numbat 争议变体 (复核模型取 llm_variants/dispute), collab 打开, 跑到首次等复核:

- CSH-02 在第 3 层执行 (CSH-04 → DOC-06 → CSH-02; 验收原文的 "第 2 层" 已由主代理按实际改正), 该层汇合后为 in_dispute, transition 一行 CSH-02 planned → in_dispute.
- 总览中 CSH-02 的 ProcedureSummary.status 为 in_dispute, pending_tasks 1; 总览 features 为 [collab, critic].
- 主流程 (BA-01 判一致, `test_main_flow_keeps_results_and_records_triggers[on]`): Store 里没有一版程序是 in_dispute, 也没有到 in_dispute 的 transition.

### 决定后重算 (验收 3)

- `test_recompute_procedure_with_disputes`: 仍有待决 dispute 为 in_dispute; 只有其他待决任务为 awaiting_human; 都没有为 completed; executing 不改; collab 关闭时有待决任务即 awaiting_human (现状). 原有的 `test_recompute_procedure` 不变.
- 争议变体 a6_upheld (D-ARB) 后 CSH-02 completed, transition in_dispute → completed; collab 关闭时为 planned → awaiting_human → completed. 两边 transition 总行数相同.
- `test_dispute_left_after_other_task_decided_stays_in_dispute` (P2 以外节点的 TST-J01, 一条 normal 一条 dispute): 先确认 normal 的, 仍有争议, 程序不出新版本; 再仲裁, completed.

### 路由 (验收 4, `test_after_fan_in_with_program_in_dispute`)

- in_dispute 的程序有待决任务时 after_fan_in 走 await_events; 以它为前置的 REV-02 不派发 (ready_procedures 只认 completed).
- in_dispute 却没有待决任务: ScheduleStuck "REV-08 为 in_dispute, 却没有待决的复核任务"; 与 awaiting_human 的一起时逐个列出; 前置卡在它上面时 "REV-02 等 REV-08 (in_dispute)".

### 排序 (验收 5)

- 对话 list_open_items: 争议变体首次等复核时复核任务依次为 T-J-CSH-02-1-BA-01-v1, T-J-REV-03-1-CON-001-v1, -002-v1, -003-v1. 按项目冻结的功能集判断: 换成基线功能集的进程读这个项目, 总览 features 与待办顺序照旧 (项目开了 collab). collab 关闭时按创建时间, REV-03 三条在前 (同现状).
- 前端 rankTasks (`src/frontend/tests/review-rank.test.ts`, bun test): 开了 collab 时两条待决争议 (一条金额很大, 一条置信度 0.95) 按创建时间排最前, 已决定的争议照旧参与档位排序, 其余与没开时的相对顺序相同; 没开时 (功能集里没有 collab 或没有功能集) 与原来的排序相同. 改坏四处 (不认 collab, 总是提前, 已决定的也提前, 争议之间不按创建时间) 都抓到.

### 前端 (验收 6)

程序页把 in_dispute 视同等人处理 (默认选中第一个等人处理的程序, 给 "去处理" 链接); 标签 "争议中" / "In dispute" 与警示色原已有. lint (biome), typecheck (tsc -b) 与单元测试 (bun test) 通过.

### 开关关闭 (验收 7)

关闭时 waiting_status 只给 awaiting_human, 待办与 rankTasks 按原来的顺序. 现有测试的断言都没改 (test_dispute.py 中 awaiting_human 的断言照过; test_recompute_procedure 用 model_construct 建的任务不带 kind, collab 关闭时不读 kind).

### P2 以外的节点 (验收 8)

- `test_dispute_task_in_node_is_in_dispute_with_collab[on, off]` (完成节点的测试程序 TST-J01 出一条 dispute 任务): collab 打开时程序为 in_dispute, 节点内等待; 仲裁 a6_upheld 读回后程序 completed, 状态中的程序取 Store 最新版本, 继续到 FIN-01 闸门. 关闭时为 awaiting_human, 其余相同.
- `test_replay_with_dispute_version_but_no_task_is_a_node_error`: Store 中程序最新版本为 in_dispute 而没有待决任务与未读回的决定: 节点报 "却是 in_dispute", 不前进.
- 目前 P2 以外的程序没有 A7 复核, 实际走不到争议; 规则与 P2 一致, 以后的程序 (如持续经营的判断) 直接适用.

### 对规格书第 12.3 节 "in_dispute 只接受仲裁" 的理解 (Q5 a)

理解为争议任务本身只能仲裁 (`ReviewQueue.allowed`: dispute 任务只允许 dispute_resolution, 现状). 程序在争议中时: 同程序的其他待决任务照常可决定; 数据变了要重跑时照常可重跑 (过期重跑把该程序置 executing, 争议任务随之关闭, 同 awaiting_human). 不另加拦截.

scratchpad/jia/r151mut.py: 在导出副本上逐个改坏 (未改时全过), 跑 test_collab, test_node_wait, test_replay, test_review_decisions, test_graph, test_dispute, test_contracts, test_features, test_fan_in, test_concierge_chat_tools, test_query, 每次复原. 14 个都抓到:
