## 方案取舍

- **导入后的状态**: 由 xero_fakes 取 `case.loader`. 不另写一套装配.
  - 账表取 `XeroDatasetLoader.tables`. R268 验收 4 写明它与 plan 的 tables 相同.
  - 文件登记取 `Supplements.uploads`, 即 plan.uploads.
- **执行一条程序**: 用 `GraphNodes.perform`. 它建执行记录 (参数按数据集声明与画像解析); Agent 出错时返回 A1 的失败片段.
  - 片段写法同节点: 在一个事务内经 `save_outputs` 写入存储, 再用 `apply_patch` 并入状态. 连库时下游能从库里读到上游 (DOC-06 要读 CSH-04 存的函证).
  - 固定集程序与新加的程序第 1 版也写入存储.
- **分层与关联目标**: 依赖闭包用 `library.closure`. 分层同 `build_schedule` (只依赖闭包外程序的在第 0 层). 关联目标同 `assemble_pack` 的 trigger 匹配. 同层的程序都以本层开始时的状态执行, 同 fan_in.
- **自动确认**: 本层程序 depends_on 中的程序, 其待复核判断用 `confirm_effects` 出 v2 confirmed (同 confirm 决定, 解释的例外随之归因), 以项目负责人写入. 复核任务不动.
- **重要性**: 用闸门的 `materiality_amounts`, 作用于 PLN-01 的候选, 所以随副本的收入变化.
- **连库确认数据已齐**: 用 `DataStore.confirm_ready`, 理由同 xero_flow, 记下当时体检不通过的项, 并写 ready 留痕.
  - 不用 `DataService.confirm_ready`: 它要求主图停在等数据, 测试台不跑主图.
- **连库的画像 ID**: 换成随机 ID, 同 R112 与 R269 的连库用例, 同一库反复建不报 VersionConflict.
- **分层 mock 的查找顺序**: 先在各根里按顺序找 `{fixture_key}.json`, 都没有再按顺序找 `default.json`. 有精确的键时不被上层的 default 盖掉.
- **RoutedLLMClient**: 在构造时把 live 包进 `BudgetedLLMClient`, 交给 live 的调用一定计入预算.
- **大模型缺省值**: 两种装配都读副本补造目录的运行副本 (`llm/`). 连库时上传处理的分类与合同抽取也用它.
- **规则预置**: 离线规则缺省为 `XERO_RULES`, 即原目录上的结果. 场景改了规则输入时用 `rules=` 换.
- **table_diff 的行 ID**:
  - 缺省取 id 字段;
  - accounts 取 code;
  - trial_balance 取 `period:account_code`;
  - employees 取 employee_id.
  - 同一张表里 ID 重复时抛错, 不悄悄吞掉.
- **自测另加一例**: 只用 T0 副本, 分不出数据取自副本还是原目录. 所以另用一个两处改动的补丁副本 (服务完成日, 出租方 ABN 登记名) 核对.
