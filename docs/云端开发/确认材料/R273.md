## 讲解

### 业务背景

- 原来 "数据已齐" 只看三张必需表 (科目表, 两期试算表, 总账) 有没有行.
- 体检 (需求 R15) 借贷不平, 分录与试算表对不上时, 照样能往下走. 后面的程序在错数据上跑, 也没有审计师知情的记录.
- 本条不阻断, 只要求审计师先看到未通过的项, 并写明为什么仍要继续; 理由与当时的未通过项进确认记录与留痕.

### 几处取舍 (偏离或补充需求原文的, 都在这里)

- "未通过" 只算体检结果 `failed` (界面上的 "不一致"):
  - `missing_data` (缺资料) 与 `pending` (还没执行) 不算.
  - 否则 Numbat 这类只缺报表草稿的项目也要写理由, 与验收 2 "体检全部通过的项目照常确认" 不符.
- 验收 1 的 "借贷平衡一项未通过": 一行借方改大 1 元, 借贷平衡必然不通过. 该科目 (2100) 的发生额同时多了 100 分, 与试算表变动对不上, 所以 "分录与试算表一致" 也不通过. 这是体检规则的正确结果, 测试按两项断言.
- 理由的写法:
  - 去首尾空白后为空, 等同没写.
  - 体检没有未通过项时写了理由也照记 (前端这时不弹框, 只有直接调接口才会带). 这样不必再分支, 留痕如实反映审计师写的.
- 重复确认 (确认已记而图仍在等, 如上次后台没启动):
  - 校验照常做, 有未通过项仍须带理由, 与 DATA_NOT_READY 重复确认时照常校验一致.
  - 人与时间保留第一次的. 理由与未通过项也保留第一次的; 只有第一次没有未通过项而这次有时, 补记这次的 (第 1 轮 R273-02, 要求写的理由不丢).
- 用 "最近一次体检" (`DataStore.checks`) 判断. 判断前先补做已不对应当前数据的体检 (`checkup_if_stale`, 第 1 轮 R273-01); 补做仍出错时按已有结果判断.
- 错误码 `DATA_CHECKS_FAILED` 定为 409, 与 DATA_NOT_READY 同类 (数据状态不允许直接确认). detail 带 `failed_checks` (体检项编号, 按 CheckId 顺序), 与 `missing_tables` 同形状.
- 未通过项只记编号, 不记当时的参数 (借贷金额等):
  - 需求要记的是 "项目".
  - 编号与 `missing_tables` 一致, 前端按编号本地化.

### 契约与存储

- `DataReadiness`:
  - `ready_reason: str | None`: 确认时写的理由, 没写为空.
  - `ready_failed_checks: list[CheckId] = []`: 确认时最近一次体检 failed 的项.
- 表 `dataset_loads`:
  - `ready_reason TEXT` 可空.
  - `ready_failed_checks JSONB NOT NULL DEFAULT '[]'`. 有缺省值, 数据集载入与导入写版本时插入的新行不必改代码 (`stores.TableLoader`, `loads_row` 都不写这两列).
- 迁移 0005:
  - 0001 按当前模型 `create_all`, 新库已有这两列, 所以用 `ADD COLUMN IF NOT EXISTS` 给旧库补.
  - 已有的确认行理由为空, 未通过项为空数组.
  - 降级删两列.
- `PostgresDataStore.readiness` 改为按 `DataReadiness.model_fields` 取列 (同 `versions` 的写法), 以后加字段不用再改查询.

### 确认 (`DataService.confirm_ready`)

- 校验顺序: ENGAGEMENT_LOCKED → ENGAGEMENT_BUSY → NOT_AWAITING_DATA → DATA_NOT_READY → DATA_CHECKS_FAILED. 缺表时先报缺表, 体检的 "缺资料" 不会叠加成未通过.
- `failed = [check.id for check in checks if check.status == "failed"]`, 按 CheckId 顺序 (存储返回的就是这个顺序).
- `reason = (reason or "").strip() or None`; `failed` 非空而 `reason` 为空时拒绝, 消息列编号, extra 为 `failed_checks`.
- 通过后 `deps.data.confirm_ready(eid, actor, reason=reason, failed_checks=failed)`. 留痕取存储返回的 `readiness`, 所以重复确认时留痕里是存储中的理由与未通过项.
- 校验在持项目锁时做, 体检也在锁内跑, 读到的未通过项与存下的是同一次体检.

### 留痕 (`data_ready_entry`)

- payload:
  - 全部通过时仍是 `{"action": "ready"}`, 与以前一样.
  - 记了理由时加 `reason`, 有未通过项时加 `failed_checks`.
- 摘要分三种: 数据集载入; 有未通过项 ("体检 N 项不通过, 写明理由后确认数据已齐, 开始计划阶段分析"); 其他.
- 恢复补写 (`GraphRunner._data_confirmed`) 用的是同一个函数与 Store 中的确认记录, 补写的留痕同样带理由与未通过项.

### 接口

- `POST /data/ready` 的请求体为可选的 `DataReadyIn {reason}`. 不带请求体的调用 (现有前端, 测试) 照旧.
- 返回的 `DataReadiness` 含两个新字段.

### 前端

- `DataReadyButton(eid, disabled, size)`:
  - 取数据概览 (`useDataSummary`) 的体检结果.
  - 有 failed 的项时点按钮先弹框: 列出各项 (标题与 `checkDetail` 的说明, 如 "借方 AUD x, 贷方 AUD y") 与理由输入框. 理由去空白后非空才能确认, 带理由提交.
  - 没有时直接确认, 与以前相同.
  - 后端报 DATA_CHECKS_FAILED (概览还没跟上最新一次体检) 时也弹框. 提交后 `invalidateEngagement` 刷新概览, 列表随之补上.
- 数据管理页顶部 (size lg) 与工作区补交资料卡片 (默认尺寸, 沿用卡片的 disabled) 都用它, 两处行为一致.
- `checkDetail` 原样挪到 `lib/data-checks.ts`, 数据管理页的体检卡改为从那里导入.
- 生成的客户端请求体为空时不带 Content-Type, 与以前的请求相同.
- 文案 (`data.readyCheck`):
  - 中文: 标题 "数据体检有未通过的项", 说明 "确认后，审计计划将按现有数据继续。请写明仍要确认的理由。", 输入框 "理由", 按钮 "确认数据已齐".
  - 英文: "Some data checks did not pass", "Planning will continue on the data as it stands. Record why you are confirming it anyway.", "Reason", "Confirm data complete".
