## 结论

- 默认测试少 70 条 (开发分支 7b8836e 上 2361 → 2291; 变基到 14e83c4 后 2461 → 2391, 到 5dd0f66 后 2559 → 2489; 多出的是其他代理新加的): 删 69 条 (只测文档措辞 67, 被覆盖或重复 1, 只核对样例数据自身 1), 合并后少 1 条 (两次补造生成合为一次); 另有 3 条复制粘贴的用例合为 1 个参数化用例 (条数不变). 删除清单见下文.
- 后端行覆盖率不变: 整理前后都是 91.26% (13909 行, 未覆盖 1215 行), 127 个文件的语句数与未覆盖行数逐个相同.
- 耗时 (整理前后在同一时段交替跑, 机器上一直有其他代理在跑测试, 墙钟波动大, 见 "耗时对比"): 串行的 CPU 时间约 343 秒 → 约 184 秒, 省约 46%; 串行墙钟两次 378 / 597 秒 → 244 / 185 秒; 4 进程并行墙钟两次 214 / 265 秒 → 123 / 222 秒. 协调者 15:40 在 60e3501 上量的串行是 324.78 秒. 省下的最大一项是程序库缓存 (一遍约 1190 次建依赖, 每次约 0.1 秒).
- 加了 pytest-xdist 作开发依赖, CI 的默认测试改为 `-n auto`; 并行安全核对 8 次全部通过, 没有要修的共享状态. `-m slow` 不能并行 (见 "并行").
- 另修了一处不干净: 假证据存储每次运行在系统临时目录留下的数十个目录, 改为用完删掉.

## 时间花在哪 (整理前)

整理前用 `--durations=0` (含 setup 与 teardown) 量了一遍, 再对最慢的文件做了剖析. 主要发现:

1. **每个用例都重新解析整套程序库**: `tests/fakes.make_deps` 每次调组装根 `build_deps()`, 其中 `ProcedureLibrary(knowledge 目录)` 用纯 Python 的 YAML 解析全部程序模板与准则片段, 还跑两次 git 取提交号, 约 0.1 秒; 整理后计数: 一遍默认测试经 make_deps 建依赖约 1190 次. 用 cProfile 剖析 `test_decisions.py`: 33.6 秒中 18.2 秒在 `ProcedureLibrary.__init__`. 这是最大的一项, 与哪个文件无关.
2. **准则原文 PDF**: `test_knowledge.py` 每取一段原文都重新打开 PDF (公司法一卷 821 页, 打开就要 0.4 秒) 并重新解析页面, 同一页被逐字测试, 正例, 反例各解析一遍.
3. **定稿文档的段号核对**: `test_xero_demo_data.py` 从 AASB 1060 等 PDF 抽原文核对 *设计文档* 引用的段号, 第一个用例就要 8 秒.
4. **重复的全流程**: `test_e2e_mock.py` 的真实 Agent 演示被 7 个用例各跑一遍, `test_blind_filter.py` 的半程运行被 5 个用例各跑一遍, "决定被拒" 的参数化用例 (共 60 个) 每个参数各从头跑一遍到闸门或等复核处.
5. **其他重复计算**: `test_api.py` 每个用例重算 argon2 口令哈希 (0.25 秒), `test_blind_filter.py` 每个用例生成一到两次 OpenAPI 文档 (约 1 秒), 补造数据被几个用例各自完整生成, 同一份补造 PDF 与日记账报表被几个用例各自解析.

## 没有动的与理由

- test_knowledge 的抽取工具自测 (整段边界, 页眉页脚, 行首记号等数十条, 用了知识库之外的准则 PDF): 它们保证逐字测试不会因抽取出错而误过或误报, 是知识库原文核对的一部分, 保留; 改为按页缓存后同一页不再重复解析.
- test_knowledge 的逐字测试仍是默认测试里最慢的一组 (首个片段读到该准则所在页才停, AASB 15 约 4 秒): 这是把知识库片段逐字核对原文的必要开销, 只读一次.
- 闸门以外的流程测试 (test_rerun_stale, test_node_wait, test_recovery 等) 每个用例从头跑一遍, 是因为每个用例接着提交不同的决定或注入不同的故障, 改的状态互不相同, 不能共用; 它们每次建依赖的那 0.1 秒已由程序库缓存省掉.
- test_merge, test_review_fields 等大量单项校验用例: 每条测一条规则, 都是纯函数, 很快, 不是重复.
- 只在 setup 里重复的构造代码 (几个文件里相同的 8 行起图代码) 不是重复用例, 本次不动.

## 并行 (pytest-xdist)

- 依赖: `uv add --dev pytest-xdist` (3.8.0, 连带 execnet), pyproject 与 uv.lock 由 uv 生成.
- 共享状态排查: 默认测试本机 4 进程跑了 5 次 (其中一次 `--dist worksteal`), 绑在 2 个核上 (`taskset -c 0,1`) 2 进程跑了 3 次, 变基后逐提交检查又各跑了一次, 全部通过, 通过与跳过数与串行相同, 跑完工作区没有多出或改动的文件. 按清单查过: 用例都用 tmp_path 或自建的临时目录; 改环境变量的用 monkeypatch 或在 conftest 里统一设 (每个进程各自一份); 没有监听端口 (HTTP 一律 MockTransport); 写仓库目录的只有生成脚本, 而它的守卫用例保证写不进仓库; 会话级的原目录哈希核对在每个进程各做一次. 没有要修的, 所以没有单独的修复提交.
- CI: `.github/workflows/ci.yml` 的默认测试改为 `uv run pytest -m "not slow" -q -n auto`. GitHub 托管的 ubuntu-latest 为 2 至 4 核, xdist 按可用核数开进程 (本环境没有 psutil, 按 sched_getaffinity, 绑核时也取得对); 上面 2 核 2 进程的 3 次即按 4 核以下的情形核对.
- 本地: 开发流程 "分支与提交" 与 "环境" 两处写明 `uv run pytest -n auto`. pre-push 钩子没有改 (仍串行), 想快可以本地自己加.
- `-m slow` 不并行: 4 进程试跑连库测试时, 迁移用例 (test_migration_0008_backfills_data_changes_under_force_rls 升降级表结构) 与导入用例 (test_import_batch_on_real_store) 互相干扰而失败, 串行照常通过; 真实大模型的会话预算 (live_session_budget) 是会话级夹具, 每个进程各算一份, 并行会放大上限. 开发流程里写明了.
- 分发方式: 缺省的 `--dist load` 下模块级 fixture 与 PDF 缓存在每个进程各算一次 (例如 test_knowledge 的准则 PDF 会被几个进程各解析一遍), 所以并行的 CPU 时间比串行多; 墙钟仍明显更短. 没有改分发方式.

## 环境限制

- 连库测试: 自建库 audit_ding (属主 audit_owner, 迁移到 head 并以属主角色建检查点表), 变基后每个提交都串行跑了 `-m slow` (57 条通过, 14 条跳过: 真实大模型没有配 LLM_MODEL 与 LLM_API_KEY, CUAD 只在 CUAD_FETCH=1 时真下载, 以及需要本机外部数据的用例).
- 计时期间机器上一直有其他代理在跑测试 (负载 3 到 12), 没等到空闲的时段; 前后对比在同一时段交替顺序跑, 另给 CPU 时间 (user + sys) 作参照. 17:55 前后另一个代理按命令名杀过 pytest, 当时被杀的那次检查已重跑; 之后的计时与检查改用 `pytest -p no:cacheprovider -q` 的写法, 不再落在那个匹配上.
