## 方案取舍

- **要扫的凭证:** 状态中全部 adjustments_posted 通知载入的凭证减去已有增量执行 (trigger incremental) 扫过的, 不只看 "本轮" 通知: 每轮都扫完时两者相同, 上一轮没扫成时下一轮补上. 通知的凭证号为空 (载入全部未载入的) 时取数据集可载入的全部更正分录 (协调者 10-20 裁定), 减去扫过的即本次新载入的. 改参数的重跑 (trigger rerun) 带 entry_nos 也不算扫过.
- **出错为节点错误:** Agent 出错或片段校验不过时不代写失败的执行与 failed 任务 (程序不出新版本, 没有任务可挂), 照常抛出记入 run_error, 恢复时重做 (已写的执行按重放取回).
- **复用:** 执行记录与 perform 共用 `new_run` (参数, 画像, 数据版本, R339 的语言); 写入用 `save_outputs`, 被测总体用 `run_population` (R324, 同 perform); 重放用 `stored_outputs`. recovery.py 不用改: 读回顺序取 node_table, GEN-05 不建任务.
- **R06 不按 entry_nos 筛 (需求原文):** 每次增量执行都按首次沟通时间重查, 第 2 轮会对同一笔分录再出一条例外 (ID 带 run_no); R06 剔除审计更正分录, 这些例外不进 FIN-09.
- **过期判定:** 增量执行算 GEN-05 最近的执行, 更正分录载入后 GEN-05 不过期, GEN-02 照旧过期 (接口文档第 7 节写明, 未改代码).
- **增量例外并入 FIN-09:** 按例外 detail.entry_no 与匹配行所在凭证对上, 只取当前结果中增量执行引出且未归因的, 按 ID 接在 V02 之后.
