# 转交需求: 程序缺数据时挂起, 智能导入, 体检理由, 过期重跑 (2026-10-19)

来源: 本地「前端开发」会话. 用户 10-19 用真实模型 (LLM_MODE=live) 从头测一个新项目时发现, 要求转给云端开发.

## 给云端的处理说明

1. 先合并本仓库 main (本文件随 main 提交), 合并提交, 不变基.
2. 按 `开发流程.md` 的格式把下面各条并入 `需求清单.md`: 总览表加行, 正文各一节. 编号从 R267 起 (被占用就顺延), 临时编号用本文的 DG-n. 需要拆小的自行拆, 粒度不超过 M.
3. 用户拍板记入 "待拍板", 作为第 10 批 (原话见下一节).
4. 排期: 用户定 "数据线马上先做", 即数据线 (R90, R95 起那条) 下一项就做本批, 复核线照常.
5. 技术细节由你定. 下文写 "建议" 的都可以改, 改了在来由里写明理由. 与现有计划相交的先对照再定: R130 (规则执行前检查, skipped / not_executable), R87 (P2 以外节点的通用等待), R21 (rerun 决定), R82 (新状态字段与旧检查点兼容), R89 (文件类型).
6. 本批含前端, 由你一起做. 界面面向审计师: 中英双语, 用词简洁专业, 不写口语化或解释性的填充文字, 不出现开发者术语 (接口名, 程序内部状态名, 错误码).

## 用户拍板 (10-19, 选择题)

- 缺数据怎么处理: 选 "逐个程序等数据": 有数据的程序先跑, 缺数据的单独挂起, 补齐后自动补跑. 未选推荐项 "执行阶段开始前统一要一次数据".
- 智能导入识别完一批文件后怎么确认: 选 "整批一张确认单" (推荐项).
- 排期: 选 "数据线马上先做" (推荐项).
- 另外两处缺口一起做: "体检不通过时确认要写理由", "过期程序要显示并能重跑".

## DG-1 程序声明所需数据, 缺数据时逐个挂起并提补交请求

- 档位 xhigh, 规模 M (超了就拆).
- 目标: 每条程序声明它要用的账表与文件类型.
  - 开跑前检查; 要用的数据为空时不执行, 程序状态记 "等待数据" (新状态).
  - 空的口径由你定, 建议账表按审计期间内的行数, 文件按该类型已确认的份数.
  - A3 为缺的每一样提补交请求, used_for 写等它的程序; 审计助理照现有 "待处理事项" 列出.
  - 有数据的程序照常跑.
  - 适用 P1 与 P2 的非人工程序, DOC-04 同样适用.
- 声明的写法 (建议): 程序 YAML 加 `inputs: {tables: [...], documents: [...]}`, ProcedureLibrary 加载时校验取值.
- 依赖与调度:
  - 依赖的程序在等数据时, 下游不派发, 沿用现有 depends_on 语义.
  - 还有程序在等数据时, 流程不进入下一阶段, 改为等待数据到达, 不抛 ScheduleStuck.
- 自动继续: 补交的数据到了 (导入提交, 文件抽取完成) 并经 A3 体检后, 请求转 received, 图在后台自动继续, 只派发数据已齐的程序. 并发按现有项目锁 (ENGAGEMENT_BUSY).
- 出口: 客户确实没有某类资料时, 审计师可在补交卡片上选 "客户无此类资料" 并写理由 (必填).
  - 等它的程序记 "未执行 (无数据)" 终态并留痕, 下游依赖照此处理.
  - FIN-01 闸门材料列出未执行的程序与理由.
  - 这一条是本地会话补的: 用户选了逐个等待, 但没有出口时流程会永远停住. 已告知用户.
- 范围 (建议): contracts (ProcedureStatus, 程序定义的 inputs, DataRequest), `knowledge/procedures/*.yaml`, `services/data_quality.py` (按等待的程序提请求), orchestration (scheduler, after_fan_in, fieldwork, nodes.execute, runner 的自动继续), 检查点白名单与旧检查点兼容 (参照 R82), 接口文档第 2, 3, 6, 7, 8 节, 前端程序页, 工作区与补交卡片, 中英文案.
- 验收:
  1. Numbat 项目只导入三张必需表: P1 的 DOC-04 等待合同.
     - 批准 PLN-01/03 后, CSH-04, CSH-05, CSH-02, REV-08, REV-02 等待数据, REV-03 因 DOC-04 未完成不派发, 没有一条在空数据上 succeeded.
     - 流程不进入 completion, FIN-04 不提前执行.
  2. 补交请求: 银行账户, 银行流水, 销售发票, 发运单各一条 (账表), 合同一条 (文件).
     - used_for 列出对应程序.
     - GET /data/requests 与审计助理 "有什么需要我处理" 都列出.
  3. 只补 bank_accounts.csv 与 bank_transactions.csv: 请求转 received, 图自动继续, 派发 CSH-04, CSH-05.
     - CSH-02 在 DOC-06 完成后才派发.
     - 各程序的例外与 Numbat 全量回归 (R55) 中对应程序一致.
  4. 全部数据都有的 Numbat 全流程 (R55, R56) 与 Xero 回归: 程序, 例外, 任务 ID 逐字段不变 (零影响).
  5. 选 "客户无此类资料" (例: 发运单) 并写理由: REV-08 记未执行 (无数据), 留痕含理由.
     - REV-02 按依赖规则处理.
     - FIN-01 材料列出 REV-08 与理由.
     - 理由为空时拒绝.
  6. 前端: 程序页与工作区显示 "等待数据" 与 "未执行 (无数据)"; 补交卡片有 "客户无此类资料" 入口; 中英文案齐; `bun run lint`, `bun run typecheck` 通过.

## DG-2 智能导入: A3 用大模型识别一批文件并规整, 整批确认单

- 档位 xhigh, 规模超过 M, 建议拆成四条: DG-2a 规整方案与确定性套用, DG-2b A3 识别, DG-2c 批次接口, DG-2d 前端.
- 目标: 审计师在数据管理页一次拖入一批文件 (Excel, CSV, PDF, Word, 图片混着), A3 自动识别每一项是什么, 怎么规整成标准数据, 生成一张确认单; 审计师看过, 点一次 "确认导入" 写入.
- 入口: 数据管理页现有的 "导入账表" 与 "上传文件" 合成一个 "上传资料" 入口. 补交卡片上的上传也走它, 带 request_id.
- 表格文件 (CSV, XLSX, XLS; 一个工作簿的每个工作表各算一项):
  1. A3 把每个工作表的前若干行交给大模型, 含标题行; 建议不超过 30 行, 只发样本, 不发全表.
  2. 大模型输出 "规整方案": 哪张表 (8 种之一), 或不是账表 (当文件处理); 表头行; 要跳过的行 (标题, 合计, 空行, 分组标题); 列与字段的对应; 需要的变形; 文件里读到的公司名与期间; 把握 (高或低) 与理由.
  3. 变形至少覆盖: 分组标题行向下填充 (如 Xero 日记账的 "ID n 摘要"); 本期与上期分列转成 period 行; 借贷两列算余额; 一列带正负号拆借贷; 取值映射 (如 Xero 科目类型 "Current Liability" 映射为 liability); 金额单位 (元或分); 日期写法.
  4. 规整方案由代码确定性地套到全表, 沿用 `services/data_import.py` 的类型转换. 大模型不输出数据行.
- 非表格文件: 走现有 A3 分类与抽取 (合同, 回函等), 结果并入同一张确认单. 文件在确认前不被程序使用.
- 确认单: 每项一行, 列出文件名与工作表, 识别为什么, 将写入的行数, 读到的公司与期间, 把握, 问题提示.
  - 标红: 把握低; 解析失败 (附前 20 处, 同现有 IMPORT_PARSE_ERROR); 公司名或期间与项目不符; 同一批里同一张表出现两次; 将替换已有数据 (写明现有行数).
  - 默认勾选全部没有标红的项; 标红项默认不勾, 审计师点开调整或确认后再勾.
  - 调整: 沿用现有列对应界面 (components/import-dialog.tsx), 预填规整方案.
  - "确认导入" 一次写入所勾选的全部: 每张表一个新数据版本, 文件按确认的类型登记, 写完体检一次. 确认前不写任何财务表.
- 大模型不可用 (mock 下没有 fixture, 未配密钥, 调用失败) 时, 退回现有按列名匹配 (suggest_kind, suggest_mapping), 该项标 "按列名匹配, 请核对".
  - mock fixture 按现有约定放 `tests/fixtures/llm/<识别程序>/<fixture_key>.json`, 识别程序的编号你定.
- 测试样例 (都在仓库里):
  1. `data/external/xero/raw/trial_balance_2026-06-30.xlsx`
     - 结构: 前 3 行标题 (Trial Balance / Demo Company (AU) / As at 30 June 2026), 第 5 行表头, 本期是 "Debit - Year to date" 与 "Credit - Year to date" 两列, 上期是 "30 June 2025" 一列, 末行 Total.
     - 预期: 识别为试算表, 6 个科目, 本期与上期各 6 行; 读到 Demo Company (AU) 与 2026-06-30.
  2. `data/external/xero/raw/journal_report.xlsx`
     - 结构: 标题 3 行, 按 Journal ID 分组, 组标题 "ID n 摘要".
     - 预期: 识别为总账分录, 368 笔, 1017 行.
     - 注意: Posted By 列是导出账号的姓名. 按计划决定 12, 不要写进 fixture 与提示词样本, 测试里先遮蔽.
  3. `data/external/xero/raw/chart_of_accounts.csv`
     - 结构: 59 个科目, Type 是 Xero 类型 (Bank, Current Liability, Expense, Fixed Asset, Direct Costs, Revenue 等).
     - 预期: 识别为科目表, 类型映射到五类.
  4. `data/external/xero/raw/receivable_invoice_detail.xlsx`: 按发票分组, 有 "Total ..." 合计行; 预期识别为销售发票.
  5. `data/demo/*.csv` (Numbat 标准列): 7 张表全部高把握, 结果与现有按列名匹配一致.
  6. 混合一批: Numbat 的三张 CSV 加 `data/demo/contracts/CON-001.pdf` 至 `CON-003.pdf`. 确认单 6 项, 合同识别为合同并带抽取要素.
  7. 期间不符: 在截至 2026-06-30 的项目里拖入 `trial_balance_2026-11-30.xlsx`, 该项标红 "期间不符", 默认不勾.
- 验收 (各子条细化): 上面 7 个样例在 mock (fixture) 下结果确定; live 下各跑一次并记入确认材料 (没有密钥就注明跳过); 确认前财务表不变; 确认后每张表的数据版本加 1, 体检只跑一次; 前端 lint 与 typecheck 通过.

## DG-3 体检不通过时, 确认数据已齐要写理由

- 档位 high, 规模 S.
- 目标: POST /data/ready 在最近一次体检有未通过项时, 不带理由就拒绝 (新错误码, 附未通过项).
