# R307 确认材料: 守卫入库的 openapi.json 与后端导出一致

来由: 需求清单 R307 (R198 第 1 轮普审意见 07). 基于开发分支 08c952e. 免审.

## 改动摘要

- `src/backend/export_openapi.py`: 抽出 `openapi_text()`, 导出脚本与守卫共用同一种写法 (不转义非 ASCII, 缩进 2, 末尾换行).
- 新 `tests/test_openapi_snapshot.py` (默认测试, 2 例):
  - 入库的 `src/frontend/openapi.json` 与 `openapi_text()` 逐字比较. 不同时以 `pytest.fail` 报出重新生成的命令 `cd src/frontend && bun run generate-client`, 附前 12 行差异.
  - 自测: 在入库文档的副本上给 ClientDataset 加一个字段, 失败信息含命令与差异行.
- `docs/云端开发/开发提示词.md` 写代码一节加一句: 后端接口一改就重新生成并一并提交, 由这条守卫查.

## 方案取舍

- 逐字比较, 不按 JSON 语义比较. 路由 docstring 也进 openapi.json 的 description, 也要重新生成; 逐字比还能顺带查出格式漂移. 失败信息带差异行, 一眼能看出是哪个模型或接口.
- 只守 openapi.json, 不另比 src/client/. 后者由 openapi-ts 从前者生成, 要 node_modules; 前端 typecheck 与 lint 已在 pre-push 里跑.
- 自测不改后端, 在入库文档的副本上加字段, 不再生成一次 OpenAPI, 只测失败信息. 真改后端的情形我手工验过 (见验收 1).
- package.json 的 generate-client 脚本不用改: 它调的导出入口没变, 写出的文本与守卫比的是同一份.

## 验收对照

1. 开发头 08c952e 上守卫通过.
   - 手工核对: 临时给 `api/schemas.py` 的 ClientDataset 加 `probe: bool = False`, 不重新生成.
   - 守卫失败, 信息为 "入库的 openapi.json 与后端导出不一致, 后端接口改了没重新生成: 运行 cd src/frontend && bun run generate-client", 下附 `+ "probe": {...}` 几行. 已还原.
   - R198 的修正还没进开发头, 开发头上照过.
2. 不读前端 node_modules, 不起服务.
   - 用时: 本机 4 核, 负载约 11, 守卫一例 1.1 至 2.4 秒, 其中 CPU 约 1.1 秒, 几乎都花在 FastAPI 生成 OpenAPI (pydantic 生成各模型的 JSON Schema).
   - 不改导出的写法就快不下来, 达不到验收写的 1 秒以内. 请协调者决定放宽这条, 或换到空闲机器上再测.
   - 自测一例 0.2 秒.
