# R325 确认材料: 执行进度留痕与进度汇总 (后端)

来由: Issue #49 验收 1, 3, 5, 6, 7 的后端. 规模 M, 档位 xhigh. 基于开发头 f236cd4 (已含 R324 的 9d422b2, c7c5333, 1a1a3dd 与 R339, R342). 变基冲突只在 import, 总览字段 (R162 的 awaiting_correction), 接口文档第 3 节 fan_in 一段与审计助理的模块说明, 两边都留; R342 把 rule_ask 改成按工作语言建总览, test_rule_model_says_what_is_running 随之改传 progress. 协调者 10-20 定方案 B: 运行中的执行记录照旧不写 Store; 开始留痕在调 Agent 之前写, 正在运行的程序按 run 留痕推出.

## 改动摘要

- 契约:
  - models: TrailKind.run.
  - views: PhaseProgress {phase, done, total, running}; EngagementOverview.progress.
- orchestration/trail.py: run_started, run_finished. 键 {eid}:run:{run_id}:started 与 :finished. payload 按需求, 只有执行状态的键名改了 (见取舍 1).
- nodes:
  - perform 在建好执行记录之后, 调 Agent 之前写 started. fieldwork 里也写. 重放时同键跳过, 缺了按重建的执行记录补写 (与 Store 中的同号同参数).
  - attempt 在事务之后写 finished, 先于 transition.
  - fan_in 在提交之后按暂存项顺序写 finished.
  - 结果摘要里的被测总体读 Store, 重放补写时也拿得到.
- services/run_summary.py: run_result (纯函数), 按程序种类给有的项. 只数 run_id 为本次执行的对象; 失败的执行为空.
- query: progress.
  - total 与 done 取 Store 中本阶段的程序, done 按 graph.SETTLED.
  - running 只在 runner.is_running(eid) 时读本项目的 run 留痕 (trail_pages.all_of_kind), 按 run_id 配对.
- 审计助理:
  - get_overview 带 progress, 正在运行的程序给编号与名称;
  - mock 规则模型加 "现在在做什么" 一类问题, 按阶段, n/m 与程序名回答.
- openapi.json 与前端 client 用 generate-client 重新生成.
- 接口文档第 2.1, 3, 6.1, 7 节.

## 方案取舍

1. 执行状态的键名是 run_status, 不是需求写的 status.
   - 原因: 留痕 payload 的 status 为 failed 时, AuditTrail.find_success 认为这次动作没做成 (函证发函等靠它重试). 失败执行的结束留痕叫 status 的话, 每次重放都会再写一遍.
   - test_trail.test_failed_run_finishes_once_with_its_reason 守住这一点.
   - R326 前端按 run_status 读.
2. P2 的结束留痕在 fan_in 提交之后写 (按方案 B). 所以同一层里已做完而还没汇合的程序, 在 running 里仍算 "正在运行": 它们的结果还没写入. test_query 用停住的 REV-08 看到同层四条都在 running 里.
3. pending_reviews 只在模板 outputs 含 review_tasks 时给. ACC-08 的判断不建任务, 所以它不给.
4. documents 数片段交回的文件. 重放补写时取回的是该类型的全部文件, 可能比第一次多. 只影响补写的那一行.
5. 改了三个列出全部留痕的现有用例 (验收 7 允许):
   - test_contracts 的 TrailKind 末尾;
   - test_replay 换了新留痕存储后的种类列表, 多了补写的两行 run;
   - test_evidence 第一次发函后的键列表, 多了开始留痕.
   - 另有 chat_fakes.make_overview 补了 progress 的缺省值.

## 验收对照

1. payload 与结果 (test_trail):
   - 留痕构造参数化 3 例: 有 scope 且日期为 date 或 ISO 文本; 重跑; 没写 scope 的失败执行.
   - run_result 参数化 5 例: 规则程序有总体, 有规则未记录, 没有总体, 判断程序, 抽取程序; 另有失败的执行一例.
   - Xero 值 (test_demo_walkthrough): RUN-REV-08-1 去重 6 张 990000, 例外 1, 三条规则 6/6/5; RUN-REV-03-1 判断 3, 待复核 3; RUN-REV-02-1 判断 6; REV-08 的 scope 中文.
2. 失败与等数据:
   - 失败的执行 run_status failed, failure_reason 同执行记录, 没有结果;
   - short_of_data 场景里只有执行过的三条有 run 留痕, 等数据的程序一条也没有.
3. 幂等:
   - attempt: Agent 执行时只有 started, 执行记录还不在 Store; finished 写入时已提交, 后接 transition.
   - fieldwork 与 fan_in: fan_in 重做, fieldwork 重放都不重复写; 删掉 finished 后重放补写, 内容相同.
   - Numbat 全流程到归档: 每次执行各一对, 键不重复.
4. 进度 (test_query):
   - REV-08 停住时为 P2 0/7, running 为 CSH-04, CSH-05, REV-03, REV-08 (按开始先后); 放行后 running 为空.
   - 按 run_id 配对: 第 1 次的结束补写在第 2 次开始之后, REV-08 仍算在运行; 别的项目不读; 不在执行时不给.
   - Xero 演示停在执行阶段等复核时 total 9.
   - done 的口径参数化 3 例: completed 与 no_data 算已结清, awaiting_human 不算.
5. 审计助理 (test_concierge_chat_service): "现在在做什么" zh, en 各一例, 另有没有在运行的一例.
6. 演示走通: 每次执行恰一对 run 留痕, 开始在前, 条数为执行数的两倍. 现有各种类的计数断言不变.
7. 除上面列的三个外, 现有用例不变; Numbat 回归照过.

变异 (scratchpad/jia/mutate_r325.py, 12 个): 配对按程序编号, 不在推进也给 running, done 只数 completed, total 不分阶段, 状态键名叫 status, 不写开始, attempt 或 fan_in 不写结束, 摘要不按执行筛, 失败也给摘要, 摘要不读 Store 的总体都被杀. 起初存活两个:
- Q03 "done 只数 completed": 补了上面 done 口径的 3 例后被杀.
- Q12 "重放时开始留痕取重建的执行, 不取 Store 中的": 等价变异, 理由如下. 代码已改为只用重建的执行, 少一个分支, 这条变异不再适用.
  - 开始留痕只用执行记录的 procedure_id, id, run_no, trigger 与 params_snapshot (渲染 scope). started_at, instance, data_version 不进 payload.
  - 重放时重建的执行按检查点状态取号, ID 与 run_no 相同, trigger 由 run_no 定. 参数快照按同一状态, 模板, 画像版本与数据集声明解析, 与 Store 中那次相同 (接口文档第 3 节重放规则 "重跑与首次相同").
  - Store 读回的参数快照日期为 ISO 文本, days_before 两种都认, 渲染出的 scope 相同.
  - 走到这一处补写, 只有开始留痕当初没写成而执行已有终态这一种情况; 其余时候同键跳过.
