# R324 确认材料: 被测总体 (契约, 规则引擎与 REV-08)

来由: Issue #50 验收 1, #49 验收 1 共用. 规模 M, 档位 xhigh. 三个提交, 都变基到开发头 84bf645: 功能提交; 严审 (6 minor, 5 nit) 的修正; 复核新提的 R324-12 至 14 (1 minor, 2 nit) 的修正. 协调者 10-20 定: P2 的总体随暂存项 (StagedResult.population) 经一次检查点, 在 fan_in 与执行记录终态同一事务写入; 占位用 prompt_env 那套 Jinja2 环境, 只加 days_before 过滤器, 加载时用 jinja2.meta 核对变量, 不加派生参数.

## 改动摘要

- 契约:
  - knowledge: LocalizedText (zh, en 都要, 去首尾空白后不为空); RuleSpec 加 population {sql, description} 与 check; ProcedureTemplate 加 scope.
  - models: PopulationItem, RulePopulation, RunPopulation (ID POP-{run_id}).
  - services: RuleResult.populations. state: StagedResult.population (NotRequired).
- 规则引擎: 执行了的规则各记一份总体. emit rows 以返回行为总体; exception 规则写了 population 时在规则 SQL 之后另执行总体 SQL, 没写的记为未记录 (count 为空); 检查命中的规则不记. 行到项目 (rule_population): 各行 source_type 相同且在 SourceType 内时才是对象类型, 各行不同或类型不认识都按混合处理 (为空, 原值留在 fields, 不报错); 行 ID 取 source_id, 没有时取 id; 其余列进 fields.
- 程序库:
  - prompt_env 与 json_default 从 judgment_engine 移到 procedure_library (避免循环引用), 加 days_before; 另有 render_text (纯函数).
  - 加载校验 population_problems, text_problems (过滤器与检验名都要认识; check 不许有 Jinja 标记); read_problems 也扫总体 SQL.
- Agent 与节点 (审核 R324-01 取方案乙):
  - ProcedureAgent.outcome(ctx) -> AgentOutput(patch, populations): 原始发现是 RuleResult 时交回其 populations, 否则为空. run(ctx) 为 outcome 的片段. RunContext 与 run_rules 不变 (纯输入, 纯调用).
  - run_agent 返回 (片段, 写入者, 总体), A1 代写失败片段时总体为空. run_population(template, run, populations) 只给 engine rule, 交回了总体且成功的执行建总体.
  - attempt 在事务内写总体. fan_in 按暂存项写, 改为失败项的不写. 重放不带总体.
- 存储: OUTPUT_KINDS 的 procedures 表加 RunPopulation.
- services/populations.py (归 B, 调用方 A, C): total_cents, distinct_items, judged_subjects, extracted_documents.
- REV-08.yaml: scope; R01-R03 的 check 与 population. 三条总体都按发票 GROUP BY, 一张发票一项; R01, R02 的服务完成记录为 records 数组 (jsonb_agg, 按记录 ID, 每条 {delivery_no, signed_date, signed_by}, 没签收的为 null; 没有记录的发票为 null): 签收人是自由文本, 写成 "姓, 名" 时逗号会打乱按位对齐的串 (R324-13). R03 的流水 ID 与收款日仍按流水 ID 逗号连接 (都不含逗号, 与规则 SQL 的 bank_transaction_ids 一致), 日期改用 to_char(..., 'YYYY-MM-DD'), 不随 DateStyle 变 (R324-14; 已在测试库 SET DateStyle = 'SQL, DMY' 下核对: CAST 成 30/09/2026, jsonb 与 to_char 仍是 2026-09-30).
- 测试辅助: fakes 的 engine_result 按 YAML 给预置结果补总体; rev08_populations 由表独立算 REV-08 的总体 (口径同上); no_population 移到 fakes.
- 接口文档第 0, 1, 2.3, 3, 5, 6, 8.1, 9 节. 第 7 节没有节点调 Agent 的条目, run_agent 记在第 5 节"被测总体与对象清单"与第 6 节.

## 方案取舍

- 总体从 Agent 到节点走明确的返回值 (outcome), 不经 RunContext 旁路. 不选把 run 改成返回 AgentOutput (方案甲): 要把约 170 处测试改成 .patch.
- 判断程序不写总体: 需求写明对象清单由 Store 推出. REV-02, CSH-02 经 run_rules 取对象, GEN-03 直接调 deps.rules.run (参数另加关联方); 三者的原始发现都不是 RuleResult, 也不是 engine rule. PLN-01 (engine manual) 同样不写.
- GEN-03 C01 一条规则合并分录与流水, 所以行类型不同时不报错.
- "分录号" 取发票的 journal_entry_id (分录行 ID). 不再连总账, 免得 REV-08 多一类过期来源.
- 抽取程序的文件登记不记执行, extracted_documents 取的是程序当前的抽取对象.
- 改了的现有用例:
  - 因 REV-08 多出总体 SQL: test_rule_engine_checks 的零影响用例 (期望查询加总体 SQL); test_rerun_stale 的逗号连接用例 (R03 的连接串出现两次).
  - 因 run_agent 多一个返回值: 22 处解包改为 `patch, writer, _`; test_completion 的打桩从 run 改到 outcome.
  - 意图都不变. 另有两处 import 随 prompt_env 搬家.
