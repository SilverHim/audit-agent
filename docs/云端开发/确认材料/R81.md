## 讲解

### 业务背景

- 规格书第 6.1 节把程序分为固定集与装配集.
  - 全量分录扫描, 关联方, 期后事项, 持续经营等每个审计都要做.
  - 它们是 P2 程序, 但不对应某条审计目标.
- 原来 P2 程序只能经 trigger 匹配审计目标, 或经依赖闭包加入. 没有 trigger 的 P2 程序 (DOC-06) 只能靠别人依赖它.
- 草稿 JR-1 与 GC-01 都要加 fixed 字段 (critique C12 指出重复定义), 本条合一.
- 本条只建机制; 后续各组的 GEN-04, GEN-06, FIN-02 等程序标 fixed 并挂功能名.

### fixed 字段与加载校验 (验收 1, 2)

- `fixed: true` 的 P2 程序:
  - PLN-01/03 通过后 assemble_pack 一律加入, 不看审计目标.
  - 所属功能未启用时不加入.
  - triggers 可为空.
- 未标 fixed 且没有 trigger 的 P2 程序仍只经依赖加入:
  - DOC-06 被 CSH-02 依赖, 照常加入.
  - GEN-09 没有程序依赖它, 不装配.
- `fixed_problems` 四条规则, 消息含程序编号:
  - 非 P2 程序标 fixed: "X-P3 不是 P2 程序, 不能标 fixed". P2 以外的程序本来就以 "triggers 为空" 进项目启动时的固定集, fixed 对它们没有意义.
  - fixed 程序的参数写 {by_risk: ...}: "X-RISK.days 按风险等级取值, 但固定集程序没有关联审计目标".
    - 参数解析按 objective_ids 取最高风险 (nodes.build_run 的 highest_risk).
    - 固定集程序的 objective_ids 为空, 取不到等级.
  - fixed 程序写 triggers (第 1 轮 R81-01): "X-TRIG 标了 fixed, 不能再写 triggers". 否则这些 trigger 会计入覆盖, objective_ids 也非空, 与 "固定集不对应审计目标" 矛盾.
  - fixed 程序依赖闭包中的 P2 程序写 by_risk (第 1 轮 R81-02): "X-DEPS 依赖的 REV-02.window_days 按风险等级取值, 只经固定集加入时没有关联审计目标". 本项目没有审计目标匹配 REV-02 时, 它只经依赖加入, objective_ids 为空, 执行时取不到窗口天数的等级. P2 以外的依赖 (如 DOC-04) 不查: 它们在项目启动时实例化, 参数不按审计目标取.
- 校验放在功能过滤之前, 对全部模板 (含未启用的) 做: 写错的模板不因功能关着而漏检.
- `fixed()` 从启用视图取, 按文件名顺序.
- 测试 `test_fixed_templates_are_checked_on_load` (test_knowledge), 按 feature 参数化 (不挂, 挂未启用的 journals):
  - 现有 knowledge 的 fixed() 为空, 全部模板 (含未启用) 都没有 fixed.
  - 临时目录分别加 X-P3, X-RISK, X-TRIG, X-DEPS: 构造抛 ValueError, 消息含编号与对应的说明.
  - 加合格的 X-OK: 启用 journals 时 fixed() 为 [X-OK]; X-OK 挂 journals 时基线的 fixed() 为空.

### 装配 (验收 3, 4)

- `assemble_pack`: 匹配集 = 各审计目标 trigger 匹配到的程序 ∪ 启用的固定集. 之后照原逻辑:
  - 按编号排序后补齐依赖闭包.
  - 只加入尚不在程序包中的.
  - 新程序第 1 版与阶段 P2_Executing 同一事务写入.
- 新程序的 objective_ids 仍为直接匹配的目标. 固定集程序不匹配任何目标, 所以为空.
- 测试辅助:
  - `fixed_library(tmp_path, features, **extra)`: 复制 knowledge 目录, 另加程序 YAML, 按功能集建程序库.
  - X-FIX: P2, fixed, triggers 与 depends_on 都空, feature journals, L3.
  - X-DEP: 同上, depends_on [X-FIX].
- `test_fixed_program_is_assembled_regardless_of_objectives` (验收 3):
  - journals 开: 新增 [CSH-05, CSH-04, DOC-06, CSH-02, REV-03, REV-08, REV-02, X-FIX].
  - X-FIX 第 1 版 planned, objective_ids [], 自主度 L3.
  - 8 条第 1 版与阶段写入在同一次提交.
  - 基线 (journals 关) 下仍新增原 7 条.
- `test_fixed_dependencies_are_closed_and_layered` (验收 4): 新增末尾为 X-FIX, X-DEP; build_schedule 中 X-DEP 的层号比 X-FIX 大 1.
- `test_fixed_programs_are_sorted_with_matched` (第 1 轮 R81-04): 编号靠前的 B-FIX 排在新增程序最前, 说明固定集与匹配集一并排序, 不是追加在末尾.

### 覆盖校验 (验收 5)

- 覆盖校验 (uncovered_objectives) 只看 trigger, 不变. 固定集程序不对应审计目标, 有它也不算覆盖.
- `test_fixed_programs_do_not_cover_objectives`:
  - 审计目标加 OBJ-INV-EXI (Inventory, Existence, high), 有 X-FIX.
  - 缺口为 [OBJ-INV-EXI]; assemble_pack 抛 ValueError, 不写.
  - 停在 PLN-01/03 闸门时 approve 报 INVALID_VALUE (R60 不变).

### 不重复加入 (验收 6)

- `test_fixed_programs_are_not_added_twice`:
  - 装配后的状态再装配: 返回空片段.
  - 同一状态再执行一次 (节点重放): 程序包与第一次相同, 各 ID 只出现一次; Store 行数不变 (put 同 ID 同版本跳过).
- PLN-01/03 驳回回到 p1_analytics, 发生在装配之前. 驳回后再通过时程序包里还没有 P2 程序, 与第一次装配相同.
- `test_fixed_program_added_once_after_reject_then_approve` (第 1 轮 R81-05, 取自审核方探针): 全图上 ACC-01 通过, PLN-01/03 驳回, 再通过 (绑定第 2 版), 停在 schedule 前: 程序包各 ID 只出现一次, X-FIX 在 Store 中只有第 1 版, objective_ids 为空.

### 现有测试 (验收 7)

- 现有 knowledge 下没有 fixed 模板, 装配与分层断言不变:
  - 第 0 层 REV-08, REV-03, CSH-04, CSH-05.
  - 第 1 层 REV-02, DOC-06.
  - 第 2 层 CSH-02.
- test_assemble 原有用例与 Numbat 全流程不变.
