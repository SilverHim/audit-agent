## 改动摘要

- `tests/tools/live_budget.py` (新):
  - `Budget(max_calls, max_input_tokens, max_output_tokens, parent)`: 用量上限与已用量, 按程序记调用与 token. `admit` 在调用前查: 已超限, 或这一次会是第 max_calls+1 次时置 exceeded 并抛 `BudgetExceeded`, 此后每次都直接拒绝; `record` 在调用后记账, 累计 token 超过上限时即置 exceeded; 测试的预算挂在会话预算下 (parent), 记账一并计入, 任一超限即拒绝. `check()` 已超限即 `pytest.fail("超出预算: 已用 n 次调用, 输入 x, 输出 y token; 被拒的调用来自 <程序>")`.

## 讲解

### 为什么要预算

- 真实大模型按调用收费, 端到端验收一次要几十次调用; 模型输出反复不合格时, 判断引擎每次最多重试 3 次, 测试的驱动又会对 failed 任务提交 rerun, 叠起来可能失控. 预算让每个测试有上限, 到了就停发并让测试失败.
- 关键的一点: 超预算的异常是在 Agent 里抛出的, 编排的 run_agent 会把它当成普通异常转成 failed 任务; 如果驱动循环照常对 failed 任务提交 rerun, 每次重跑都会再撞上限 (reject 很快, 但流程不会结束, 也看不出是预算的问题). 所以驱动在每次提交决定之前查预算, 超了直接失败, 不进入 rerun.
- 上限只按调用次数与 token, 不写单价 (各家价格会变); 给了单价才折算金额. 上限不保证覆盖最坏情况: 一次调用用了多少 token 只有调用之后才知道, 超 token 上限的那一次已经发出 (并发时同时在途的几次也已发出), 之后的才拦住.

### 验收

1. `test_calls_over_the_limit_are_not_sent` (预算 3 次: 第 4 次不调内部客户端, 抛 BudgetExceeded, 置 exceeded, 之后都拒绝), `test_concurrent_calls_get_only_the_remaining_calls` (并发 10 次只放行 3 次), `test_failed_calls_count` (抛错的调用也计数), `test_tokens_over_the_limit_stop_further_calls` (输入与输出 token 两种), `test_usage_accumulates_by_procedure_and_into_the_session`, `test_install_budget_wraps_main_and_review_models_once` (主模型, 判断引擎与复核模型共用一个预算; 装两次不重复包; 不是 SwitchableLLMClient 时报错).
