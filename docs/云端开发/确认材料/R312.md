# R312 确认材料: 真实模型走通暴露的输出截断与指针问题

## 改动摘要

- `adapters/llm.py`, LiveLLMClient:
  - **截断**: 解析失败且 finish_reason 为 length 时, error 写截断说明 `TRUNCATED` (英文, 写实际发出的上限), raw 照常保留. 服务端回输出达上限的 400 时不抛错 (`output_limit_reached`), 返回 raw 为空, token 记 0, error 同上. 两种都由校验按语法失败回传重试.
  - **输出上限封顶**: 400 说输出上限超出模型所允许并给出 N 时 (`output_cap`), 本客户端此后以 N 封顶, 立即重发.
  - **超时**: 缺省读超时 600 秒, 建连 15 秒 (`TIMEOUT`).
  - 读 400 错误体的三个函数共用 `error_of`.
- `contracts/knowledge.py`: `LLMSpec.max_tokens` 缺省 4096 改为 32768. `agents/sheets.py`: DOC-SHEET 去掉显式的 4096, 走缺省.
- `services/judgment_engine.py`:
  - 判断改用 `JUDGMENT_SYSTEM`, 写明规则例外不是证据来源, 不把例外 ID 写进指针.
  - 重试时上次原文为空就不追加 assistant 消息.
- `services/llm_settings.py` (测试连接): 回复没解析出来时提示带上原因 (如被截断); 上限 64 改为 1024.
- 接口文档第 4, 5, 8, 10, 11 节.
- 用例在 `test_llm_live`, `test_llm_call`, `test_llm_settings`, `test_judgment_engine`.

## 复现与来由

验收 1. 协调者用密钥跑 scratchpad/r312/repro_gen02.py (不入库), 对象 XJ-397, prompt 6203 token:

| 上限 | finish_reason | completion | 其中推理 | 正文 |
|---:|---|---:|---:|---:|
| 4096 | length | 4096 | 4096 | 0 字符 |
| 16384 | stop | 5764 | 2235 | 13740 字符 |

截断推断成立: 推理 token 把上限用光, 正文为空.

验收 4, 5. 协调者查了 audit_int 的 ENG-2026-1130:
- **对象为空的 GEN-02 failed 任务**: RUN-GEN-02-1 失败, 原因是输出达上限的 400 (LLMTransportError). 已随验收 2 修.
- **trail 指针**: J-CSH-02-1-BA-091 v1 (A6) 的 evidence 与推理链都引了 trail X-CSH-02-1-D04-1, v2 (A1 争议裁决) 原样带着.
  - 引用级照现行设计把它标 unsupported 并保留, A7 也因此被触发.
  - 根因是提示词没说规则例外怎么引.

## 方案取舍

- **截断**: 缺省上限 32768 (协调者定), 截断说明回传.
  - 只封顶, 不增加实际用量. 不做 "重试时加倍上限" (要改契约).
- **上限超出模型所允许 (第 1 轮 R312-01)**: 照协调者定的做法, 沿用 400 参数自适应.
  - 从错误信息取允许的上限: OpenAI "supports at most N", DeepSeek, 通义 "[1, N]". message 或 param 须提到 max_tokens 或 max_completion_tokens.
  - 封顶后重发的上限严格变小; 取不出数或已不大于 N 时照常抛错, 不会循环. 不加配置项, 不按服务商写死.
- **认输出达上限的 400**: error.param 与 code 都为空, 只能认 message, 改认两种写法共同的开头 "could not finish the message because".
- **指针**: 不改引用级, 不新增指针类型, 只在判断的系统提示词写一句, 全部判断程序都受用.
- **显式上限**: DOC-SHEET 改走缺省 (原值等于旧缺省, 同样会截断). DOC-STATEMENTS 8192 不动 (Issue #46 的 R321 整条删掉它). DOC-CLASSIFY 512, GEN-09 第二轮 1024, DOC-REGISTRY 2048 是有意压小的短输出, 首跑都一次通过, 保留.
- **测试连接的上限 64 改为 1024**: 推理 token 计入上限, 64 可能还没写正文就用完, 测试连接会误报失败. 只封顶, 不增加用量.
- **超时**: 只放宽读超时, 建连仍短 (地址不通时 15 秒内报错).
  - 读超时仍按传输层重试 3 次, 每次重新生成并计费, 最坏约 40 分钟, 期间项目锁不放. 本条不改.

## 验收对照

1. 复现: 见上表.

## 审核结论

- 第 1 轮普审不通过 (1 major, 4 minor, 2 nit), 7 条全部按意见与协调者定的做法改了:
  - R312-01: 400 封顶.
  - R312-02: 认共同开头.
  - R312-03: 测试连接带原因, 上限 1024.
  - R312-04: 建连 15 秒.
  - R312-05: DOC-SHEET 走缺省.
  - R312-06: 空原文不追加.
  - R312-07: 只在解析失败时写截断说明.
- 第 2 轮普审通过, 第 1 轮 7 条都解决. 剩下的两条也改了:
  - R312-08 (minor): 错误体给出的允许上限小于 1 时照常抛错, 不再以同一上限一直重发; 封顶判断改用 `is not None`; 补 "at most 0" 用例.
  - R312-09 (nit): 接口文档第 4 节与类说明开头的 "max_tokens 透传" 补上 "得知允许的上限后以它封顶".
