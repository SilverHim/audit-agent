- 新增 `orchestration/waits.py`: 等待载荷的登记与判断.
  - `WaitKind` {review, human, correction, data}, 字符串值与已有检查点一致 (data 为合并上游后加, 即 p1_await_data 的等数据).
  - `review_payload(phase)`, `human_payload(procedure_id, run_id, records)`, `data_payload()`.
  - `kind_of(payload)`: 载荷的种类, 认不出为 None.
  - `accepts(payload, task, pack)`: 该等待能否接受对某个任务的决定.
- `orchestration/nodes.py`:
  - attempt: 程序新版本按 `pending_tasks` 定 (本程序在片段写入后仍有任一待决任务即 awaiting_human), 不再只看片段里的 failed 任务.

## 讲解

### 业务背景

- 原来 P2 以外的程序 (ACC-04, DOC-04, PLN-07, PLN-01, FIN-04, RPT-03) 只在失败时于节点内等人, 只认 rerun 决定.
- 后续各组的完成阶段程序 (持续经营 GC, 期后事项 SE 等) 会在 P2 以外出判断与复核任务, 须在节点内等人复核.
- critique C9 合并了草稿 MD-4, SG-3, AP-15 的等待部分, 并指出两处问题:
  - decisions.py 对不带 procedure_id 的载荷一律放行: 停在 await_events 时, P2 以外程序的任务也能提交进去.
  - recovery.py 同一程序同一轮有多个决定时抛 RuntimeError ("无法确定读回顺序"), 而非 rerun 的决定一轮可以有多个.
- 测试程序 TST-J01 放在临时 knowledge 目录 (完成阶段, owner A6, hybrid, L2, outputs [judgments, exceptions, review_tasks]); 完成节点改为先 TST-J01 后 FIN-04 (monkeypatch NODE_PROCEDURES); Numbat 走完 P2 与复核后进入完成阶段.

### 等待规则 (验收 1)

- attempt 写入片段与程序新版本后, 本程序在 Store 中仍有待决任务 (normal, unattributed, dispute, failed 等, 含之前各次执行留下的) 时为 awaiting_human, 节点 interrupt().
- 取回决定后:
  - 针对 failed 任务的决定 (或找不到任务的): 走 read_rerun, 须为 rerun 且针对本轮的任务 (Q17: 一轮失败算一组, 整组重跑), 然后以 run_no + 1 重跑. R05 的 "决定不对" 三例 (不存在, 不是 rerun, 不针对本轮任务) 照样报节点错误.
  - 其余决定: 任务须属于正在等待的程序 (否则节点错误), 从 Store 整体读回本程序的任务, 判断, 本程序的例外与判断引用或任务指向的例外, 由这些判断与例外认定的错报, 针对这些任务的决定. 各字段按 ID 排序, 并入的结果与提交顺序无关 (Q9).
  - 每次 interrupt() 之前 (每轮执行之后的第一次, 每读回一个决定之后) 都只按 Store 判断: 本程序仍有待决任务, 或 Store 中有针对本程序任务而尚未读回的决定 (如本轮的 failed 任务已被一个尚未送到的 rerun 决定关闭) 时再等. "已读回" 含检查点里已有的 (之前进入本节点时读回的), 同一图节点先执行的程序读回的, 以及本次读回的 (第 1 轮 R87-01).
  - 不再等时节点结束: 这一轮的程序版本当时就不等人则用它, 当时在等则取 Store 最新版本 (DecisionSubmit 已重算: completed, 闸门程序为 planned).
- 节点于是按决定数逐个经过等待, 等待次数与决定交回的顺序无关 (第 1 轮 R87-02): 在线先 rerun 后 confirm, 恢复补做按 "非 rerun 先" 交回, 结果相同. rerun 决定仍须按轮次交回 (read_rerun 只收针对本轮的).
- 写进接口文档第 7 节恢复机制.

### 载荷 (验收 2, 7, 9)

| 种类 | 载荷 | 接受的决定 |
|---|---|---|
| review (await_events) | {awaiting: review, phase: P2_Executing} | 程序所在阶段为载荷 phase 的任务; 旧检查点不带 phase, 按 P2_Executing |
| human (P2 以外节点等人) | {awaiting: human, procedure_id, run_id, records} | procedure_id 那条程序的任务 |
| correction (等待更正, 错报段用) | 本条只登记 | 一律不收 (NOT_AWAITING_REVIEW) |
| data (P1 开始前等数据就绪, 上游 p1_await_data) | {awaiting: data} | 一律不收; DecisionSubmit 先由 review_waits 排除, accepts 也为假. 确认数据已齐 (POST /data/ready) 后以 DATA_READY 恢复 |

- human 载荷的键与现有失败等待相同. records 只列本图节点读回的决定: 同一图节点先执行的程序读回的 (p1_analytics 中 PLN-07 重跑用过的, 传给 PLN-01), 加上本程序读回的. 原来还列入检查点里已有的全部复核决定 (Numbat 进入完成阶段时有 6 个), 验收 2 要求 TST-J01 第一次等待的 records 为 [], 故改. DecisionSubmit 判断 "须先恢复" 时检查点里的决定本来就算, 不受影响.
- `accepts` 按程序包查任务所属程序的阶段.
