# R300 确认材料: 程序视图显示未执行的规则与理由

来由: R130 方案第 6 题, 第 5 批裁定 "在程序视图显示". 规模 S, 只改前端, 不改后端, 接口与生成的客户端.

## 改动摘要

- 新 `src/frontend/src/lib/rule-outcomes.ts` (纯函数), 共三个:
  - `notRunRules`: 一次执行没有执行的规则, 按记录顺序; 没有这一项时为空;
  - `outcomeStatuses`: 要说明含义的状态, 只取出现过的, not_executable 在前;
  - `outcomeTone`: 标签色调, not_executable 为 warn, skipped 为 neutral.
- 程序详情页 (`routes/engagements/$eid/procedures/$pid.tsx`):
  - 执行记录一节每次执行下, 有未执行的规则时加一个框 "未执行的规则".
  - 框里每条一行, 写规则编号, 状态标签与理由; 下面说明出现过的状态的含义.
  - 全部执行了的执行记录不显示这个框.
- 文案 `procedureDetail.notRun` (中英), 含义口径同接口文档第 2.3 节 RuleOutcomeStatus.
  - 无法执行 / Not executable: 本应执行, 但缺数据或参数, 补齐后重跑.
  - 跳过 / Skipped: 按设计不适用于本项目.
- 测试: 新 `tests/rule-outcomes.test.ts`, 4 例.

## 方案取舍

- 框放在每次执行下面, 不另起一节: rule_outcomes 是一次执行的属性, 重跑前后各次可能不同.
- 两种状态用色调区分, 说明只写出现过的状态: 全是跳过时不必解释 "无法执行". not_executable 排在前面, 因为要审计师处理.
- 规则按记录顺序列, 不按状态重排: 记录顺序就是 YAML 中的规则顺序, 与规则发现的例外编号一致.
- 理由原样显示, 不翻译: 理由是程序作者在检查 SQL 里写的数据. 没写时, 后端已换成 "前置检查未通过".
- 只显示规则编号: 程序详情接口 (ProcedureDetail) 不带规则名, 要显示得改后端, 这超出本条范围.

## 验收对照

1. 列出编号, 状态与理由; 全部执行时不显示:
   - 用例: 按记录顺序列出 3 条; 空列表与旧记录 (没有这一项) 都为空.
   - 界面: PLN-07 第 1 次执行下列出两条. A02 为 "跳过", 理由是检查写的字面量; A03 为 "无法执行", 理由列为空, 显示缺省理由 "前置检查未通过".
   - 界面: 全部执行了的 PLN-01 没有这个框.
2. 两种样式不同, 文案说明含义:
   - 用例: 两种色调不同; 只说明出现过的状态, 顺序固定, 不重复 (4 组输入).
   - 界面: 两个标签的类分别是 bg-warn-soft text-warn 与 bg-muted text-secondary-foreground, 两句说明都在.
3. 前端检查与 Playwright: 见下. 截图 zh-1-PLN-07.png 与 en-1-PLN-07.png 在 scratchpad/r300/, 不入库.
   - 数据是真实的, 不改浏览器收到的响应. 后端连自建库 audit_bing269, 知识目录用临时副本 (核对后已删): PLN-07 的 A02 加一个 skipped 检查, A03 加一个理由为空的 not_executable 检查.
   - 准备步骤: 建 Numbat 项目 → ACC-01 通过 → `seed load` 载入数据集 → POST /data/ready → 跑到 PLN-01/03 闸门.
   - PLN-07 的 rule_outcomes 由真实规则引擎在 Postgres 上写出.
