# R127 确认材料: 客户画像扩展字段与 profile. 参数引用

来由: 草稿 JR-2. 规格书第 4.3 节的客户画像字段由本条一次定义. 程序参数可以用 `{ref: profile.<字段>}` 取本项目采用版本的画像值. 本条是 R288 (客户登记与新建客户) 的前置.

## 审核结论

规模 M, 档位 high. 开工前交了方案, 五题的裁定 (协调者, 10-19):

1. 已有库里的旧 Xero 画像 v1: 不做数据迁移, 也不手工清理. 照 "改一律出新版本, 旧版本不覆盖" 处理:
   - 建项目时数据集的画像与该客户的各版比较内容 (不看版本号): 有一版相同就沿用最新一版, 都不同才写新一版 (第 1 轮审核 R127-01 改定, 原为只与最新一版比较).
   - 新库上仍是 v1; 老库上出 v2, 项目采用最新一版.
   - 慢测试不写死版本号; 用假存储的默认测试照旧断言 v1.
2. optional 只用在 profile. 上.
3. 每次 perform 都按版本读一次画像.
4. Xero 画像的 notes 去掉已写进字段的两项.
5. resolve_params 的 profile 为必填关键字参数.
6. 定稿第 2.6 节的 JSON 块一起改 (需求范围外, 已同意): test_xero_demo_data 断言 client_profile.json 等于这一块.

第 1 轮独立审核通过 (无 blocker, major; 27 个变异全被抓到), 3 条 minor 与 2 条 nit 按协调者裁定修改, 改完不再复审 (见文末 "第 1 轮审核的修改").

## 讲解

- 为什么 create 要改: 补造画像改了内容但仍为 v1. 之前在 Xero 演示上建过项目的库里存着旧的 v1, 按原逻辑再建 Xero 项目会报 VersionConflict. 现在这种库会出 v2, 新库照旧是 v1. 已存的版本都不改.
- 审计师改过的画像: 数据集画像与已存的某一版相同, 说明数据集没变, 新项目沿用最新一版 (含审计师改过的), 不把数据集原样写成新的最新一版. 只有数据集画像与各版都不同 (数据集本身改了) 才出新版本; 这时最新一版即数据集的新内容, 审计师之前改的那一版作为旧版本保留不改.
- 画像按版本读: 参数在建执行记录时解析, 写入 params_snapshot. 同客户的另一个项目把画像改到 v2 后, 本项目 (采用 v1) 的参数仍取 v1; 重放时以 Store 中的参数为准.
- optional 只给 profile.: dataset. 本来就以 None 执行; 重要性等状态 ref 为 None 时不能执行; 加了 optional 会把 "尚未确定" 的重要性当作 None, 所以加载时拒绝.
- 现有程序 YAML 都没有引用 profile., 所以 Numbat 与 Xero 的执行结果不变. 第一批用到的是 R131 (GEN-05 的审批限额) 与 R190 (RPT-03 的上期是否经审计).
