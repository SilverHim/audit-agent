## 讲解

### 三个索引各给哪些读法

| 读法 | 调用处 | 条件与排序 | 用的索引 |
|---|---|---|---|
| 最近一页 (newest) | 工作台时间线, GET /trail?newest=true | 本项目, 可带一组 kind; (created_at, id) 倒序, limit | TRAIL_BY_TIME 倒着扫, 取够 limit 条即停 |
| 往前翻 (before) | 同上, 以上一页最早一条为游标 | 同上, 另加 (created_at, id) < 游标那条 | TRAIL_BY_TIME (游标那条的 created_at 用主键取) |
| 按类型逐页读完 | trail_pages.all_of_kind | 本项目, kind = 一类; (created_at, id) 正序, 每页 500 | TRAIL_BY_KIND |
| 按类型取最近一条 | AuditTrail.last_of | 本项目, kind = 一类, payload.action 在一组内; 倒序取一条 | TRAIL_BY_KIND 倒着扫, 过滤 action |
| 按防重复键取 | AuditTrail.find_success | 本项目, idempotency_key = 键; (created_at, id) 正序 | TRAIL_BY_KEY 取出这个键的几条, 再排序 |

- 工作台时间线带的 kind (transition, decision, deferral, data, conversation, 见前端 lib/timeline.ts) 是 IN 一组, 不是等值.
  - 按 TRAIL_BY_KIND 取时要分几段取出再合并排序;
  - 按 TRAIL_BY_TIME 倒着扫, 过滤 kind, 取够一页就停, 更省. 所以时间线归 TRAIL_BY_TIME.
- find_success 在每写一条带键的留痕前都查一次 (orchestration/trail.record_transitions, recovery.record_once).
  - 没有 TRAIL_BY_KEY 时它走 TRAIL_BY_TIME, 逐条比键, 要扫过本项目的全部留痕.
  - 部分索引只收带键的行 (不带键的留痕不进索引), 查询条件 `idempotency_key = 键` 本身就排除了空值, 规划器能用上它.
  - 一个键至多几条 (失败重试再成功), 取出后排序不贵, 所以不把 (created_at, id) 放进这个索引.

### 要不要含 kind 的索引

结论: 加. 只取一类的读法在轮询与常用页面上都有, 而这一类往往只占本项目留痕的一小部分:

- 数据管理页的概览 (DataService.summary, 处理中时前端每 3 秒轮询):
  - demo_summary 用 all_of_kind 取全部 data 留痕, 再 last_of 取最近一次演示导入;
  - Xero 连接状态 (xero_link.last_sync, profile_check 等) 用 last_of 取 data 留痕三次.
- 复核与延后:
  - 复核任务详情与延后列表 (reviews.py, deferrals.py) 用 all_of_kind 取 deferral 留痕;
  - 判断失败的任务另取 llm_call.
- 审计助理: 每轮对话重建记忆时 all_of_kind 取 conversation 与 conversation_summary; 列待办时取 deferral.

只有 TRAIL_BY_TIME 时, 这些读法也走索引, 但要按时间扫过本项目的全部留痕, 逐条比 kind. 留痕里数量多的是 llm_call, transition 与 data; deferral 与 conversation_summary 很少, 为了它们扫过全部最不划算.

代价: 每写一条留痕多维护两个索引 (防重复键的只在带键时). 留痕只增不改, 写入量是每次大模型调用, 状态转移与审计师操作各一条, 开销可以接受.

### 为什么关掉顺序扫描与排序

- 项目条件来自行级安全, 是 `engagement_id = current_setting('app.engagement_id', true)`. 规划时不知道是哪个项目, 只能按 "每个项目的平均行数" 估计.
- 测试库 audit_yi2 里有 2694 个测试项目, 留痕约 2.6 万行, 每个项目只有几条. 估出来每个项目约 9 行.
- 这时规划器认为先用位图把本项目的行取全, 再排序最便宜.
- 不关时实测 (audit_yi2): newest 与 before 都是 "Bitmap Index Scan on ix_audit_trail_engagement_kind_time" 加 Sort. 用的是哪个索引, 取决于统计信息, 不稳定.
- 真实部署项目少而每个项目的留痕多, 估计值大, 规划器会选按顺序扫的索引, 取够 limit 条就停.
- 要索引给出顺序的六种读法, 测试关掉排序与顺序扫描, 看的是 "索引能不能直接按 (created_at, id) 的顺序取到". 关掉后实测:
  - newest, before, 带时间线 kind 的两种: "Index Scan Backward using ix_audit_trail_engagement_time";
  - 只取一类的一页: "Index Scan using ix_audit_trail_engagement_kind_time";
  - last_of: "Index Scan Backward using ix_audit_trail_engagement_kind_time".
- find_success 只关顺序扫描, 排序留着. 实测:
  - 不关或只关顺序扫描时, 都是 "Index Scan using ix_audit_trail_engagement_key" (Index Cond 含项目与键) 加 Sort;
  - 连排序也关掉时, 规划器反而改用 TRAIL_BY_TIME 逐条比键. 因为这个索引本来就不提供顺序, 关排序对它不适用.
- 没有对应索引时只剩顺序扫描 (或另一个索引), 计划里没有这个索引名, 断言失败. 变异自查里删掉索引后即是如此, 见环境限制.

### 测试怎么拿到真实的查询

`test_trail_reads_use_the_indexes` 不重写 SQL:
1. 先写三条留痕 (data, transition, deferral), 其中 transition 带防重复键.
2. 在引擎上挂 `before_cursor_execute`, 截下 PostgresAuditTrail 这次读取真正发出的 SELECT 与参数 (IN 一组已展开).
3. 在本项目的事务里 (transaction 设好 app.engagement_id, 行级安全的项目条件同真实查询) `EXPLAIN` 它.
4. AuditTrail.list, last_of 或 find_success 的写法以后改了, 测试照样跟着它走.

### 验收

1. audit_trail 上有 (engagement_id, created_at, id) 的索引 `ix_audit_trail_engagement_time`. 另有含 kind 的 `ix_audit_trail_engagement_kind_time` 与防重复键的部分索引 `ix_audit_trail_engagement_key`, 理由见上.
2. 连库 `test_trail_reads_use_the_indexes`, 7 个参数, 计划中都出现对应的索引名 (不断言代价数值):
   - newest, before, timeline_newest, timeline_before (带时间线的五类): ix_audit_trail_engagement_time;
   - one_kind_page (all_of_kind 的一页), last_of: ix_audit_trail_engagement_kind_time;
   - find_success: ix_audit_trail_engagement_key.
3. 迁移 (`test_migration_0015_round_trip`):
   - 以属主角色在一个事务里, 先断言三个索引都在, pg_indexes 的定义为:
     - `(engagement_id, created_at, id)`;
     - `(engagement_id, kind, created_at, id)`;
     - `(engagement_id, idempotency_key) WHERE (idempotency_key IS NOT NULL)`.
   - 降级后三个都没了; 升级两次 (可重复执行) 后又在, 定义同上; 最后回滚.
   - 模型声明的列与之相同, 部分索引的条件为 `idempotency_key IS NOT NULL`.
   - 测试库的留痕表有数据, 新库的情形见偏离第 3 条.
   - 现有全部测试不变 (见环境限制).
