## 讲解

### 业务背景

数据改了以后, 用旧数据跑过的程序结论可能已不成立. 4826767 起按 "最近一次执行的数据版本 < 当前版本" 标过期, 任何一次写入都让全部 P1, P2 程序过期, 也没有重跑入口. 本条把过期收窄到 "读到变动数据的程序及其下游", 并让审计师在签字前用新数据重跑执行阶段的过期程序, 以新结果为准.

### 过期判定 (验收 1)

- 每次数据版本 +1 都在同一事务里记下变了哪类数据 (`data_changes`). 判定只读 `DataStore.changes()` 这一个来源.
- 程序 YAML 的 `reads` 登记程序读的数据. 规则 SQL 中 FROM, JOIN 后的账表名由程序库加载时核对; Agent 另读的 (REV-02 的发运单与合同, CSH-02 的函证) 手写.
- 过期: 最近一次执行记了数据版本 v, 而 reads 中某类在 v 之后变过; 或依赖的程序过期; 或依赖的程序最近一次执行开始得比它晚 (只重跑了 REV-08 时 REV-02 随之过期); 或依赖的程序最近一次执行已被重跑取代 (第 3 轮补). 承接阶段与没执行过的不算; 没有当前结果的 (已被重跑取代而还没有新执行, 在等数据或未执行) 也不算 (第 3 轮 R274-15).
- 各类数据变动时过期的程序 (Numbat 的执行全部记版本 1 时): accounts → PLN-07, PLN-01; trial_balance → PLN-07, PLN-01, CSH-05, CSH-02; journal_entries → CSH-02; sales_invoices, delivery_notes → REV-08, REV-02; bank_accounts → CSH-04, DOC-06, CSH-05, CSH-02; bank_transactions → REV-08, REV-02, CSH-05, CSH-02; contracts → REV-03, REV-02; confirmations → CSH-02. `test_stale_by_what_each_program_reads` 逐类核对.
- 能重跑的 (Q2 a): 执行阶段的过期程序, 不在等重跑 (executing), 不在等数据或未执行. 计划阶段的过期只标记.

### 重跑入口与走向 (验收 2)

- `rerun_stale` 写法同其他决定: 锁定 → 项目锁 → 功能集 → RESUME_REQUIRED → 位置 (NOT_RERUNNABLE: 只在等复核, FIN-01, RPT-01 闸门前) → 所列程序 (INVALID_VALUE) → 请求 ID.
- 一个事务内写请求, 程序 executing 新版本 (前置已记未执行而不在本次重跑里的直接记 no_data, 第 3 轮补), 这些程序的待决任务 decided (Q3 a: 由重跑关闭, 列入请求与留痕), 已过执行阶段时阶段回 P2. 提交后写 decision 与 transition 留痕, 再以 fan_in 身份写检查点, 由 after_fan_in 照现有规则派发 (新 Run 为 run_no + 1, trigger rerun, 记新数据版本).
- 之后照常复核新结果; P2 结清进 completion, FIN-04 出 SCHEDULE 下一版; 此前的 FIN-01 决定绑旧版本, 闸门重新呈报, 旧决定再提交报 VERSION_MISMATCH.
- 不改闸门登记表, 不加闸门出口. 三处起点 (等复核, FIN-01, RPT-01) 各有测试.

### 当前结果

- 被取代的执行 (请求的 superseded_run_ids) 的判断, 例外与由它们认定的错报留作历史, 不删, 不再计入: 汇总表, FIN-01 材料, REV-02 与 CSH-02 取前置程序的例外, REV-02 取 REV-03 的合同判断. 人工判断 -H 的 run_id 是任务所属的执行, 随之取代; 来源查不到的错报照旧计入.
- R21 的部分重跑 (rerun_subject_ids) 不在其中: 只重判上一轮失败的对象, 那些对象上一轮没有判断, 旧执行的其余对象仍是当前结果; 与需求 "部分重跑只取代 rerun_subject_ids 中的对象" 等价.
- 没有重跑请求时即状态中的全部, Numbat 与 Xero 全流程的计数不变 (原有测试全过).

### FIN-01 材料 (Q5 a)

材料的错报只列当前结果的, 另列 `stale_procedure_ids` (过期而未重跑的程序), 只提示不拦截. 例: 只重跑 REV-08 时回到 FIN-01, 材料列出 REV-02, 照样能通过.

### RPT-03 (Q4 a)

从 RPT-01 重跑时, 请求记下当时最新报告的修订号 (report_revision). FIN-01 重新通过后起草下一稿: 有针对上一稿的退回决定时按退回; 否则有 report_revision 等于上一稿的重跑请求时按非退回的重拟 (previous 照给, annotations 为空, addresses_decision_id 为空, 提示词说明上一稿未被退回); 都没有照旧报错. 退回之后到 RPT-01 之前图不停在可重跑的位置, 两种起因不会针对同一稿.

### 签字锁定 (验收 3)

签字 (RPT-01 approve) 后项目 locked, 重跑报 ENGAGEMENT_LOCKED, 总览 can_rerun 为假; 测试从 RPT-01 重跑一轮, 再签字后核对.

### 恢复补做

请求写入 Store 后留痕或检查点没写成时, 再提交报 RESUME_REQUIRED; resume/recover 由 `catch_up_rerun` 补写缺的留痕, 以 fan_in 身份写入提交时的同样字段 (请求, 程序包, 关闭的任务, 阶段), 之后与在线相同. 图不在可重跑的位置时报错不写.

### 阶段留痕键

原键 `{eid}:transition:engagement:{eid}:{新阶段}` 只按新阶段去重, 重跑后再进执行, 完成, 报告阶段会被当成已写. 改为状态中有 n 个重跑请求时带 `:{n}` (没有重跑时与原来相同, 已有留痕不变); 重跑请求写出的回退计入它自己, 恢复补做同键.

### 偏离方案与说明

- 方案写 reads 取值为 TableKind 加 contracts, confirmations, categories; 实际不单列 categories: 科目分类是科目表的一列, 读科目表的程序 (PLN-07, PLN-01) 都读分类, 改分类记 accounts, 结果相同.
- 写审批日志会改总账分录的审批列, 另记 journal_entries (`table_changes`).
- (第 1 轮改) 程序执行之外写进的合同都记 contracts 变动: 审计师修改, 上传或改类型后 A3 抽出的新合同版本; 回函副本的抽取不进函证, 不记. 程序执行写出的 (DOC-04 合同, DOC-06 函证) 靠依赖传播.
- 接口放在 `api/routes/reviews.py` (与程序详情同处), 前端函数名为 `reviewsRerunProcedures`.
- 总览另加 `can_rerun`, 程序详情加 stale, rerunnable, superseded_run_ids, 供 R281 显示按钮与历史结果.
