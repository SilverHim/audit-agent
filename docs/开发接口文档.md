# 开发接口文档（Demo 版）

定义 [Demo需求文档.md](Demo需求文档.md) 中各模块之间的接口：领域对象、编排状态、存储与外部接口、服务、Agent、编排入口、知识文件、数据库表、HTTP API。接口以外的实现由负责人自定。

A：智能体与编排；B：数据库与数据；C：前端与 API。

## 0. 约定

| 项 | 约定 |
|---|---|
| 语言与库 | Python 3.13、Pydantic v2、LangGraph 1.x、FastAPI、SQLModel |
| 领域类型 | 只在 `src/backend/contracts/` 定义，其他包只引用 |
| 模型配置 | `model_config = ConfigDict(frozen=True, extra="forbid")`；修改一律 `model_copy(update=...)` 并 version +1 |
| 命名 | Python 与 JSON 字段都用 snake_case；枚举用 `StrEnum` |
| 金额 | 整数分，字段名以 `_cents` 结尾；币种 AUD |
| 时间 | `datetime` 存 UTC；报告日等业务日期用 `date`，按 Australia/Sydney 取当天 |
| 项目隔离 | 存储接口的每个方法第一个参数都是 `eid`（engagement_id）；EngagementStore、UserStore 除外 |
| 版本 | 存进审计产出表的对象都继承 `Versioned`（`id` + `version`），每次修改追加新版本，旧版本不覆盖 |

**ID 规则**。同一次执行重放得到同样的 ID。

| 对象 | ID |
|---|---|
| Engagement | `ENG-{yyyy}-{nnn}` |
| Procedure | 程序编号，如 `REV-02` |
| ProcedureRun | `RUN-{procedure_id}-{run_no}` |
| AuditException | `X-{procedure_id}-{run_no}-{rule_id}-{n}`，n 按 SQL 结果顺序 |
| Judgment | `J-{procedure_id}-{run_no}-{subject_id}`；人工建的加后缀 `-H{n}`，run_no 取任务 run_id 的编号 |
| ReviewTask | `T-{target_id}-v{target_version}`；带 subject_id 的 failed 任务为 `T-{target_id}-{subject_id}-v{target_version}` |
| ReviewRecord、GateDecision | `D-{uuid4}` |
| Misstatement | `M-{review_record_id}` |
| Confirmation | `C-{bank_account_id}` |
| Contract | 合同 PDF 文件名主干（`CON-001.pdf` → `CON-001`）；B 保证 sales_invoices.contract_id 用同一编号 |
| ContractTerm | `{contract_id}-T{n}`，n 按页码与出现顺序 |
| AuditReportVersion | `REPORT-{revision}` |
| 闸门材料 | 每个项目固定：`SCORECARD`、`ANALYTICS`、`MATERIALITY`、`SCHEDULE` |
| Document | `DOC-{sha256 前 12 位}` |
| TrailEntry | `TR-{uuid4}` |

## 3. 编排状态（contracts/state.py）

```python
StatePatch = dict[str, Any]                      # EngagementState 的键的子集

class StagedResult(TypedDict):                   # fieldwork 执行一条程序一次的结果
    procedure_id: str
    run_id: str
    writer: AgentId                              # 执行程序的 Agent；执行失败时为 A1
    patch: StatePatch                            # 要写入的片段，含本次 Run 的终态

class EngagementState(TypedDict):
    engagement_id: str
    phase: Phase
    version_snapshot: dict[str, str]
    acceptance_scorecard: AcceptanceScorecard | None
    client_profile_version: int                  # 本项目采用的客户画像版本；ACC-04 按它读画像，ACC-01 路由据此判断评分卡是否过期
    analytics: AnalyticsResult | None
    materiality_candidates: MaterialityCandidates | None
    materiality_cents: int | None                # 这三项与 opinion_route 只在图状态中，不进 AuditOutputStore
    performance_materiality_cents: int | None
    clearly_trivial_cents: int | None
    audit_objectives: list[AuditObjective]
    risk_register: list[RiskItem]
    procedure_pack: list[Procedure]              # 全部 17 条的实例：固定集在 start 时建，P2 程序由 assemble_pack 加入
    schedule_table: list[ScheduleRow]
    documents: Annotated[list[DocumentRef], replace_by_id]
    staged_results: Annotated[list[StagedResult], staged] # fieldwork 实例的返回，fan_in 校验后并入
    procedure_runs: Annotated[list[ProcedureRun], upsert_by_id]
    exceptions: Annotated[list[AuditException], upsert_by_id]
    judgments: Annotated[list[Judgment], upsert_by_id]
    review_tasks: Annotated[list[ReviewTask], upsert_by_id]
    confirmations: Annotated[list[Confirmation], upsert_by_id]
    report_versions: Annotated[list[AuditReportVersion], upsert_by_id]
    review_records: Annotated[list[ReviewRecord], append_unique]
    gate_decisions: Annotated[list[GateDecision], append_unique]
    misstatements: Annotated[list[Misstatement], append_unique]
    uncorrected_schedule: UncorrectedSchedule | None
    opinion_route: OpinionType | None
```

| reducer | 规则 |
|---|---|
| `upsert_by_id` | 新 ID 追加；version 更高的替换；version 相同的忽略；version 更低抛 `VersionConflict` |
| `replace_by_id` | 按 id 追加，同 id 后到者替换 |
| `append_unique` | 按 ID 追加，已存在的忽略 |
| `staged` | 追加；收到 `None` 时清空，只由 fan_in 发出 |

没有 reducer 的列表字段（audit_objectives、risk_register、procedure_pack、schedule_table）每次写入都传完整列表。

**程序执行范围**。schedule 只对 phase = P2_Executing 的程序分层派发；fan_in 的状态重算与 after_fan_in 的"全部 completed"也只看这些程序。P0、P1、P3、P4 的程序由所在节点直接执行，执行期间不另写 executing 版本；执行完出新版本：要写入的片段有 pending 任务（整次失败时 A1 建的 failed 任务，或 Agent 建的单对象 failed 任务）为 awaiting_human，节点写入后在节点内 `interrupt()` 等人处理（见第 7 节恢复机制），否则为 completed；闸门程序（PLN-01）执行成功后的新版本仍为 planned，由 DecisionSubmit 在 approve 时置 completed。一个节点依次执行几条程序（p1_analytics 先 PLN-07 后 PLN-01）时，后一条在前一条的结果之上执行。assemble_pack 要求每条审计目标至少被一条程序的 trigger 匹配，否则阻断（节点报错，不写入）；新加入的 P2 程序第 1 版（objective_ids 为直接匹配的目标，只经依赖加入的为空）与阶段 P2_Executing 同一事务写入 Store 与 engagements 表；schedule 只排调度表，派发时不写 executing 版本。completion 由 A9 执行 FIN-04，阶段 P3_Completion 与 FIN-04 的执行写入同一事务；FIN-01 驳回后回到 completion，以 rerun 再执行，SCHEDULE 出下一版。

**字段写入归属**。A1 合并前校验：写入字段在归属范围内、类型匹配、ID 唯一、版本不低于状态中已有的且同版本内容一致、外键成立（片段把某对象改出新版本时，状态中以其原版本为目标的待决任务须在片段中一并更新，否则任务过期）（Judgment 的 procedure_id 在 procedure_pack 中、run_id 在 procedure_runs 中）。任一不过，该次执行标 failed，片段不合并。

**写入顺序**。节点返回前，A1 在一个事务内把本次新增或变更的对象 `put` 进 AuditOutputStore，片段含 documents 时同一事务内调 `EvidenceStore.set_status`，然后以 put 返回的对象写入状态，再由 LangGraph 写检查点。

fieldwork 实例不写 Store，只返回 staged_results：派给它的程序依次各执行一次，都以派发时的状态快照为准，Run 记实例名，每条程序一个 StagedResult；Agent 抛异常或片段校验不过时，该项为 A1 写的失败 Run 与 failed 任务，同实例其余程序照常执行。一次派发的实例数不超过 PARALLEL_CAP，不同层的实例同时就绪时按调度表顺序派到上限，其余下一轮派。合并前校验分两处：fieldwork 取得 Agent 片段时全量校验（以派发时的状态为准），不过的暂存为 A1 写的失败片段；fan_in 逐项再按已并入本轮前面各项的状态查 ID、版本与外键（同轮几项合起来可能冲突，如前一项把某例外改出 v2、后一项仍交回 v1，或前一项建了指向 v1 的待决任务、后一项把它改为 v2），不过的项改为 A1 写的失败 Run 与 failed 任务。fan_in 把各项按上述顺序 put 后并入状态，同轮合规项照常写入；本轮执行过的程序在同一事务内各出新版本：该程序仍有 pending 任务（含之前各次执行留下的）为 awaiting_human，否则为 completed，rerun_subject_ids 清空；随后清空 staged_results。staged_results 为空时（await_events 之后）只清空，不写。

**重放规则**。节点在写 Store 之后、写检查点之前中断，恢复时会重跑。run_no、revision、`-H{n}` 按检查点状态取号（节点内 rerun 的 run_no 见第 7 节恢复机制），重跑与首次相同；新执行（不是重放）写程序新版本时，Store 中已有更新的版本则接在其后；执行一条程序前先查该 Run 是否已在 Store 中且为终态，是则直接取 Store 中该 Run 下的对象返回，不再调 Agent、LLM 与外部接口，也不重取当前时间。取回范围按执行它的 Agent 的返回字段（第 6 节）：带 run_id 的对象（例外、判断、任务，含 A1 代写的 failed 任务）按 run_id 取各自最新版本；不带 run_id 的产出（评分卡、分析结果、重要性候选、审计目标、风险清单、汇总表、报告、函证）取 Store 最新版本；文件取 `FinancialDataStore.documents`；再补齐引用：片段中对象（判断、评分卡、分析结果）的 exception_ids 与任务的例外目标所指的例外取最新版本，以片段中对象为目标的复核任务取最新版本（例外被决定改出新版本时，指向旧版本的任务在同一事务里已置 decided），片段中对象所属的其他 Run 一并取回；片段含项目里只有一份的产出（评分卡、分析结果、重要性候选、汇总表）时，本程序之后的 Run 也一并取回（回退到较早的检查点重放时，最新产出可能来自之后的执行，下一次执行须接着取号）；之后的 Run 还有待决任务（那次节点正在等人）时，重放恢复不了那次等待，作节点错误，须从最新的检查点恢复；补齐后外键仍不成立（Store 与检查点对不上）时作节点错误。执行失败的 Run 只取它本身与任务，写入者为 A1。fieldwork 同样按此规则取回，作为暂存项。

| 级 | 校验 | 不通过 |
|---|---|---|
| 语法 | LLMResponse.output 非空 | 把 raw 与解析错误追加进 messages 重试，最多 2 次 |
| 结构 | 通过 output_model 校验；枚举合法 | 同上 |

**置信度**。`confidence = Σ w_i · c_i / Σ w_i`，只对适用的分量求和。c_evidence 为 evidence_required 中已取得证据的比例，按 reliability 加权；c_rule 为规则结果与结论方向一致取 1、矛盾取 0，仅 hybrid；c_llm 为 self_confidence。权重读 rules.json。

## 7. 编排入口（orchestration/）

```python
class EngagementRunner(Protocol):
    async def start(self, eid: str) -> None: ...        # 取得项目锁，新建线程（thread_id = eid），后台推进到第一个中断后立即返回
    async def resume(self, eid: str) -> None: ...       # 后台执行出错后手动重试：先按 recover 的规则补做，再从当前检查点继续
    async def recover(self) -> None: ...                # 应用启动时对全部项目按下文规则处理
    def is_running(self, eid: str) -> bool: ...         # 以项目锁是否被持有为准
    def run_error(self, eid: str) -> str | None: ...    # 最近一次后台执行的异常，成功推进后清除；供 EngagementOverview.run_error

class StateQuery(Protocol):
    async def overview(self, eid: str) -> EngagementOverview: ...
    async def gate(self, eid: str) -> GateView | None: ...      # 不在闸门返回 None

class DecisionSubmit(Protocol):
    async def submit(self, eid: str, decision: ReviewRecord | GateDecision) -> None: ...
        # 取得项目锁 → 校验 → 一个事务内写入决定及其效果 → 提交后写 decision 留痕 → 后台恢复流程，立即返回；
        # 校验不过或写入时 VersionConflict 抛 DecisionRejected
    async def update_client_profile(self, eid: str, profile: ClientProfile, *, updated_by: str) -> None: ...
        # 更新客户资料：取得项目锁 → 校验 → 一个事务内保存新版本画像并改项目采用的版本 → 提交后写 decision 留痕
        #   → 后台恢复流程，立即返回
```

**并发**。同一项目同时只允许一个图执行。`start`、`resume`、`submit`、`update_client_profile` 先取项目锁，取不到抛 `DecisionRejected("ENGAGEMENT_BUSY")`；取到后以 `asyncio.create_task` 在后台推进图，锁一直持有到图停在中断或结束。因此这三个方法返回时 `is_running` 已为真。demo 只跑单个 uvicorn worker。

**recover 规则**。对全部项目取检查点快照（已结束的由第 1 条跳过）：
1. next 为空，跳过。
2. decisions 表中有检查点里没有的决定，或 Engagement.client_profile_version 高于检查点的（事务已提交、恢复未完成），按下文"恢复机制"补做，并按 find_success 补写缺失的 decision 留痕。比的是本项目采用的画像版本：同客户的其他项目改画像不触发补做。
3. next 含 gate_acc01、gate_p1_risk、gate_fin、gate_rpt01 之一（静态中断不产生 interrupts），或任一 task 带 interrupts，跳过。
4. 其余（进程中途被杀、task.error 非空）调 `ainvoke(None, config)`。

**决定的效果**（A1 在同一事务内写入；decision 留痕在提交后写，见表后）：

| 决定 | 效果 |
|---|---|
| confirm | Judgment 置 confirmed |
| override（normal） | 旧 Judgment 置 overridden、记 superseded_by；按 override_conclusion 建人工 Judgment，继承旧 Judgment 的 exception_ids，置 confirmed |
| override（unattributed） | 按任务的 procedure_id、run_id、subject_id 建人工 Judgment，exception_ids 为该例外，置 confirmed |
| misstatement | 按 misstatement_draft 建 Misstatement（ID 为 M-{review_record_id}，status uncorrected）；normal 任务：Judgment 置 confirmed（并归因其例外），错报记 judgment_id；unattributed 任务：例外置 attributed（attributed_by 为空），错报记 exception_id |
| rerun | Procedure 出新版本：params 合并 rerun_params，rerun_subject_ids 追加任务的 subject_id（任务 subject_id 为空时置空，整条重跑），status 置 executing（该程序另有待决任务时也是）。程序已是 executing（前一个 rerun 尚待派发）时同样出新版本：追加 subject_id；前一个为整条重跑（rerun_subject_ids 为空）时仍整条重跑。P2 程序由下一次派发建 trigger = rerun 的 Run；P2 以外的程序由所在节点恢复后重跑 |
| manual_result | 按任务的 procedure_id、run_id、subject_id 与 manual_result 建人工 Judgment，置 confirmed |
| ACC-01 | approve：ACC-01 置 completed，phase = P1_Planning；reject：ACC-01 置 completed，phase = Declined，最后置 locked；insufficient_info：重呈，等客户补资料 |
| 更新客户资料 | 画像出新版本（id 取项目 client_id，version 为该客户画像最新版本 +1），Engagement.client_profile_version 改为新版本；client_profile_version 写入状态，评分卡依据的画像版本落后，路由回 p0_intel 重跑 ACC-04 后重呈 |
| PLN-01/03 | approve：PLN-01、PLN-03 置 completed，应用 edits（RiskItem version +1，写入新等级、revision_reason 与 approved_by = 决定人；重算审计目标的 risk_level，取其下风险项的最高等级，变了才出新版本），按 materiality 算出三个金额（整体重要性 = 所选基准金额 × pct，执行重要性 = 整体重要性 × performance_pct，明显微小 = 整体重要性 × clearly_trivial_pct，比例按十进制计算，各自四舍五入到整数分），进装配；reject：回 p1_analytics，候选重算后 version +1；insufficient_info：重呈 |
| FIN-01 | approve：FIN-01 置 completed，opinion_route = disposition，phase = P4_Reporting；reject：回 completion；insufficient_info：重呈 |
| RPT-01 | approve：该版报告置 signed，report_date 为当天，RPT-01 置 completed，phase = Archived，最后置 locked；reject：回 report_draft，A10 按批注出下一 revision；insufficient_info：重呈 |

- 人工 Judgment（override、manual_result 建的）只填人给的：conclusion 取 override_conclusion 或 manual_result.conclusion；evidence 在 override（normal）时继承原判断、override（unattributed）时取例外的、manual_result 时取人填的；confidence 1.0，confidence_parts、reasoning_chain、counter_argument 为空，proposed_action accept，autonomy_level L1，performed_by 为 reviewed_by，created_at 为 decided_at。ID 的 -H{n} 取检查点状态中该判断对象未用的最小号。
- 凡 Judgment 置 confirmed（含自动关闭与人工建的），其 exception_ids 中的例外置 attributed，attributed_by 填该 Judgment ID；已为 attributed 的不再出新版本（`review_queue.attribute_exceptions`）。
- 决定写入后，DecisionSubmit 重算目标程序的状态：本次为 rerun 时为 executing；否则程序已是 executing（之前的 rerun 尚待派发）时不改，仍有 pending 任务为 awaiting_human，没有为 completed；状态不变不出新版本。复核决定的写入者为 reviewed_by，其效果、任务 decided 与程序新版本为 A1；写入后以 `Command(resume=record_id)` 恢复。
- 置 locked 后 archive 节点与 Declined 终点不再调 put，只写留痕。
- 以上所有决定后，任务置 decided，写一行 `decision` 留痕（闸门决定记在 ACC-01、PLN-01、FIN-01、RPT-01 下）。留痕是独立事务，在业务事务提交后、写检查点前写入，idempotency_key 为决定 ID（更新客户资料为 `{client_id}-v{version}`）；写失败时与检查点未跟上同样处理：再提交报 RESUME_REQUIRED（已置 locked 的项目按校验顺序先报 ENGAGEMENT_LOCKED），由 resume/recover 补做并补写。

**恢复机制**（A 内部）。DecisionSubmit 写入 Store 的对象与标量原样进入图状态，不在节点里重新构造：
- 闸门是 `interrupt_before` 静态中断。写入后用一次 `aupdate_state(config, values, as_node=<该闸门节点>)` 写 gate_decisions 与该决定的效果：变更后的 procedure_pack、risk_register、audit_objectives（传完整列表）、report_versions、phase、materiality_cents 三项、opinion_route，以及决定绑定的材料（Store 中的版本，使路由按同一版本判断决定是否过期）。效果按 Store 中的当前版本计算（风险清单与审计目标读 Store，与校验一致），只写出本次新出的版本；Store 已有内容不同的同版本时整体回滚，报 VERSION_MISMATCH。检查点随即越过闸门，next 由闸门节点出边的路由函数按 gate_decisions 中本闸门最后一条确定（它绑定的材料不是当前版本，或当前没有材料时，留在闸门重新呈报）（ACC-01 先查评分卡依据的画像版本是否落后于 client_profile_version，落后则回 p0_intel）；然后 `ainvoke(None, config)`。
- 更新客户资料同样用一次 `aupdate_state(config, {"client_profile_version": 新版本号}, as_node="gate_acc01")`，然后 `ainvoke(None, config)`。
- 复核在节点内 `interrupt()`。写入后 `ainvoke(Command(resume=record_id), config)`，节点确认该 ReviewRecord 在 Store 中后，读回本项目复核决定、任务、判断、例外、错报与程序的最新版本整体并入状态（DecisionSubmit 写入的对象与重算后的程序版本都在其中）。record_id 在 Store 中不存在时抛 LookupError，写明原因与恢复办法：恢复值一经交给 `interrupt()`，节点出错后再恢复仍取回同一个值，须先以 fan_in 身份重写检查点（`aupdate_state(config, {}, as_node="fan_in")`），再让图继续执行（`ainvoke(None, config)`），图重新停到等复核后再提交决定。节点停在第二次及以后的 `interrupt()`（P2 以外程序失败后的节点内等待）时，检查点快照的 next 为空，等待体现在待执行任务的 interrupts 上。
- P2 以外的程序（ACC-04、DOC-04、PLN-07、PLN-01、FIN-04、RPT-03）失败时，所在节点在一个事务内写入失败的 Run、failed 任务与该 Procedure 的 awaiting_human 新版本，然后在节点内 `interrupt()`，载荷为 `{awaiting: "human", procedure_id, run_id, records}`，records 为本次图节点已读回的决定 ID（含同一节点先执行的程序读回的，如 p1_analytics 中 PLN-07 重跑用过的；图节点返回前它们不在检查点里）；Agent 的片段带 pending 的 failed 任务（如 DOC-04 单份合同失败）时同样先写入片段再等待。interrupt() 返回 record_id 后，节点从 Store 读回该决定（须为 rerun，且针对这次失败建的任务）与它写出的 Procedure 版本（awaiting_human 版本号 + 1，status 为 executing，含合并后的 params 与 rerun_subject_ids；不取最新版本，因为节点重放时会依次经过多次等待，最新版本可能来自之后的决定），以失败 Run 的 run_no + 1 建 trigger = rerun 的新 Run，在同一次节点执行内重跑；再失败则重复这一步。每次执行后的 Procedure 新版本 rerun_subject_ids 清空。一次执行留下多个 failed 任务（如 DOC-04 两份合同失败）时逐个决定、逐个重跑：本节点各次执行留下的 failed 任务还有待决的，执行后的 Procedure 仍为 awaiting_human，节点继续等待；决定可针对其中任一个，已读回过决定的任务不再接受。恢复时节点从头执行，已是终态的 Run（含 failed）按第 3 节重放规则取 Store，各次 interrupt() 依次取回已提交的 record_id。节点结束时返回历次执行写入的对象（含失败的 Run 与已决定的任务）与读回的决定。
- recover 补做时，闸门效果从 Store 与该决定重建，重要性三项按 GateDecision.materiality 与 MaterialityCandidates 重算。

## 10. HTTP API（C 实现）

前缀 `/api/v1`。除登录外都要 `Authorization: Bearer <JWT>`；访问不属于自己的项目返回 404。错误体：

```json
{"detail": {"code": "VERSION_MISMATCH", "message": "目标对象已更新到 version 3"}}
```

请求体校验失败沿用 FastAPI 默认的 422 格式。

| 方法与路径 | 请求 | 响应 |
|---|---|---|
| `POST /auth/login` | 表单 `username`、`password` | `{access_token, token_type: "bearer"}` |
| `GET /users/me` | — | User |
| `POST /engagements` | `{period_start, period_end, dataset}` | 201 EngagementOverview（running 为真）。客户由数据集的客户画像决定：handler 取 `DatasetLoader.client_profile(dataset)` 调 `EngagementStore.create`，再 `await runner.start(eid)` |
| `GET /engagements` | — | `list[EngagementSummary]`：id、client_name（取客户画像 legal_name）、phase、current_gate、pending_tasks、updated_at |
| `GET /engagements/{eid}` | — | EngagementOverview |
| `POST /engagements/{eid}/resume` | — | 202；调 `runner.resume`，用于 run_error 非空时重试 |
| `GET /engagements/{eid}/gate` | — | GateView；不在闸门 404 NOT_AT_GATE |
| `POST /engagements/{eid}/gate-decisions` | GateDecisionIn | 202 `{id}`；handler 直接 `await submit(...)` |
| `PUT /engagements/{eid}/client-profile` | ClientProfileIn | 202；handler 直接 `await update_client_profile(..., updated_by=当前用户 ID)`；只在停在 ACC-01 闸门时可用，当前画像取 GateView 的 client_profile |
| `GET /engagements/{eid}/review-tasks?status=pending` | status 可选 pending、decided | `list[ReviewTaskView]`：task、procedure_name、target（Judgment、AuditException 或 ProcedureRun）、allowed_decisions（取 `deps.queue.allowed(task)`） |
| `POST /engagements/{eid}/review-records` | ReviewRecordIn | 202 `{id}`；同上 |
| `GET /engagements/{eid}/procedures/{pid}` | — | ProcedureDetail：procedure、name、depends_on、standards、runs、exceptions、judgments |
| `GET /engagements/{eid}/judgments/{jid}?version=` | version 可选，缺省为最新 | JudgmentDetail：judgment、versions、review_records |
| `GET /engagements/{eid}/exceptions?procedure_id=` | — | `list[AuditException]` |
| `GET /engagements/{eid}/documents` | — | `list[DocumentRef]` |
| `GET /engagements/{eid}/contracts` | — | `list[Contract]` |
| `GET /engagements/{eid}/evidence/{document_id}` | — | `application/pdf`；前端用 `#page=N` 跳页 |
| `GET /engagements/{eid}/records/{source_type}/{source_id}` | — | 一行明细，JSON 对象 |
| `GET /engagements/{eid}/confirmations` | — | `list[Confirmation]` |
| `GET /engagements/{eid}/misstatements` | — | `{items: list[Misstatement], schedule: UncorrectedSchedule \| null, materiality_cents, opinion_route}`；后两项取自 overview |
| `GET /engagements/{eid}/reports` | — | `{versions: list[AuditReportVersion], decisions: list[GateDecision]}`，decisions 为 RPT-01 的全部决定 |
| `GET /engagements/{eid}/trail?kind=&limit=100&offset=0` | — | `list[TrailEntry]` |
| `GET /engagements/{eid}/trail/{trail_id}` | — | TrailEntry |
| `GET /standards/{fragment_id}` | — | StandardFragment |

GateDecisionIn、ReviewRecordIn 为 GateDecision、ReviewRecord 去掉 id、version、decided_by / reviewed_by、decided_at，这几项由服务端填写。ClientProfileIn 为 ClientProfile 去掉 id（服务端取项目 client_id），version 填当前版本 +1。EngagementSummary、ReviewTaskView、ProcedureDetail、JudgmentDetail 由 C 在 `api/schemas.py` 定义，字段见上表。

| 错误码 | HTTP |
|---|---|
| BAD_CREDENTIALS | 401 |
| NOT_FOUND、TASK_NOT_FOUND、NOT_AT_GATE（GET） | 404 |
| ENGAGEMENT_BUSY、RESUME_REQUIRED、TASK_NOT_PENDING、NOT_AWAITING_REVIEW、NOT_AT_GATE（POST）、VERSION_MISMATCH | 409 |
| DECISION_NOT_ALLOWED、MISSING_FIELD、FIELD_NOT_ALLOWED、INVALID_VALUE | 422 |
| ENGAGEMENT_LOCKED | 423 |

**前端约定**。
- 前端客户端由 OpenAPI 生成（`bun run generate-client`）。
- `running` 为真或 `run_error` 非空时禁用所有决定按钮；`running` 为真时每 2 秒轮询 `GET /engagements/{eid}`；`run_error` 非空时显示错误与重试按钮。
- 证据指针按 source_type 打开：行类型调 `/records/{source_type}/{source_id}`；document 取 `/evidence/{source_id}` 并跳到 `#page=N`；standard 调 `/standards/{source_id}`；trail 调 `/trail/{source_id}`。
