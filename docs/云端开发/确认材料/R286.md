## 讲解

**选这三份底稿的理由:** 都不在 R247 的 10 份金标准里, 所以演示与评测互不干扰.

| 合同 | 底稿 | 对应关系 |
|---|---|---|
| CON-X01 (SOW No.2 门户模块开发) | Clickstream Application Development Agreement, 11 页, 单个文件 | 开发方对客户; 底稿的 "完工后协助部署到客户环境" 与 "部署后客户验收确认", 对得上 3.1 与 4.1 |
| CON-X02 (托管支持) | TriZetto Technical Infrastructure Maintenance Agreement, 4 页 | 硬件, 操作系统与网络的维护; 抬头格式与 X02 相同 |
| CON-X03 (驻场项目管理) | MeritLife Master Services Agreement (RadialSpark 对 Clear Capital), 10 页 | 管理咨询按时计费; 现场工位, 遵守现场规定, 同等人员替换 |

**为什么第 4-7 节一字不加:**
- DOC-04 的条款 text 按 "子条款连号照抄" 取 (设计稿 6.1, R97 的 fixture 也按此写), 多一个 4.2, 5.3, 6.2 或 7.3 就会改变 11 条条款的 text.
- 新内容只放在 3 处:
  - 第 1-3 节的新子条款与 Background 段.
  - X01 第 2 页的 3.2, 3.3.
  - 第 7 节之后的新节.

**不取的条款 (会动结论):**
- Clickstream 4(b) 终止时按已完成工作付款. 取了会使 AASB 15 第 35(c) 段成立, X01 由某一时点确认翻成随时间确认, REV-03 与 REV-02 都会变.
- 作品与知识产权归属: 是第二条控制权转移.
- 质保与缺陷修复: 可能抽成 guarantee.
- 分期付款, 延误违约; TriZetto 的续约, 调价, 逾期费, 按小时计费, 质保, 部件归属; MeritLife 的调价, 报销, 成果归属, 终止付款, 反贿赂终止, 保险金额, 独立承包人 (可能抽成 related_party).

**措辞:**
- 第 4-7 节逐行冻结在测试常量里 (按页).
- 其余各行避开付款, 风险与所有权, 验收与交付, 退货, 贷项与折扣, 报销与费用, 逾期, 终止, 担保, 赔偿与关联方的字样.
- 测试列出允许的例外, 只有 X02 原有的两行 (2.1 的 "terminated earlier under clause 7", 3.1 的 "will pay a Monthly Fee").

**行数与页数:**
- X01 [39, 19, 37], X02 [27, 10, 44], X03 [43, 6, 39]. 每页上限 56 行, 每行最长 94 字.
- 每份仍 3 页, 共 29 份 57 页.

**会变的:**
- 3 份合同的文件 ID: CON-X01 DOC-00d1f7a96285 → DOC-7795e9312e9f; CON-X02 DOC-079cffb50819 → DOC-02c5c90d4ffb; CON-X03 DOC-3e9f7e6da651 → DOC-c90b3e398274 (第 1 轮修改后的值, 变基到含 R127 的开发分支后重新生成, 没有变; 修改前一度为 DOC-28bda23b5763, DOC-0e4c697d585e, DOC-192e05b0653f, 未合入, 也没有别处用过).
- 全仓 grep 旧 ID, 只有 manifest 用过. 文档, fixture 与测试都没有写死.
- 还没写的 R97 (DOC-04 fixture) 与 R267 (DOC-CLASSIFY fixture) 会用新 ID, 所以本条须在它们之前合入.

**出处行:** 不写底稿公司名, 免得 DOC-04 把它当成当事方. 测试断言底稿公司名 (Clickstream, InfinixSoft, TriZetto, MMMW, RadialSpark, Clear Capital, MeritLife 等) 都不在合同 PDF 里.

   - 3 份合同各以一份 CUAD 合同为底稿 (开发, 维护, 服务类, 与 Demo Company 的 IT 服务业务相近), 改写成 Demo Company (AU) 与其 Xero 客户之间的合同.
   - 当事方, 合同编号, 金额, 日期与控制权转移条款不变:
     - `test_contract_pages` 与 `test_contract_links_and_delivery_notes` 不改, 照常通过.
     - 新增 `test_contract_rewrite_keeps_key_terms`: 第 4-7 节逐行等于改写前 (按页冻结); 金额只有原来那几个 (X01 $6,500.00/$650.00, X02 $500.00, X03 $700.00/$4,200.00/$350.00); 日期只有原来那几个; 第 4-7 节以外没有收入条款的措辞 (例外只有 X02 原有两行); X01 不含 ABN; 每份 3 页且每页不超过 56 行.
   - 设计稿第 6 节的预期 (DOC-04 的 3 个合同, 11 条条款与证据页, REV-03 的 3 条判断, REV-02 的 6 条判断) 所依据的原句与页次都没动.
   - 现有 fixture 不受影响: Xero 的 DOC-04 与 DOC-CLASSIFY fixture 还没有, Numbat 的不涉及.
2. **页眉与 manifest:**
   - 每页页眉仍是 "Synthetic – for demonstration only. ..." 原文, 校验脚本 check_synthetic 照常核对.
   - manifest files 段的 3 份合同记 `base {dataset "CUAD v1", file <CUAD 文件名>}`, 其余文件没有 base. 见 `test_contract_bases_in_spec_manifest_and_readme` 与 `test_manifest_layout`.
3. **README:**
   - 补造目录 README.md 写 "Contract Understanding Atticus Dataset (CUAD) v1, The Atticus Project, CC BY 4.0.", Zenodo 链接, 许可链接, CUAD 免责句, Atticus 使用条款 (隐私政策与免责声明链接), "已改写" 与改写方式, 3 份底稿文件名.
   - 每份合同第 3 页签字后有出处行与许可链接, 不写底稿公司名 (`test_contract_pdfs_credit_cuad_without_naming_the_base`).
   - 生成脚本与下载脚本的署名, 链接与免责句常量相同.
4. **没有 CUAD 时:**
   - 生成脚本照常生成, 并打印 "没有 CUAD (...): 跳过合同底稿的核对 ...; 合同 PDF 按规格生成, 不受影响. 取 CUAD: uv run python -m tests.tools.cuad_fetch".
     - 实测: 把 CUAD 目录指到不存在的路径, 生成到仓库外, 输出与入库的补造目录 `diff -r` 相同.
     - 测试 `test_generator_without_cuad_prints_the_hint_and_same_files` 断言提示与逐字节相同.
     - 测试 `test_check_without_cuad_notes_the_fetch_command` 断言说明原文.
   - 已入库的合同 PDF 不依赖 CUAD. 默认测试里需要 CUAD 的只有 `test_cuad_sources_match`, 没有 CUAD 就跳过.
   - 有 CUAD 时 (本机已用 R245 的命令取到) 核对通过; 底稿不符时报出文件名 (`test_cuad_source_problems_are_reported`: sha256 不符, 底稿缺失, 取用原句找不到, 底稿 PDF 缺失).
   - 规格 base 记录有误时报出 (`test_contract_base_records_are_checked`, `test_spec_base_records_are_checked`).
5. **改写不影响设计稿已定的数字** (方案阶段已报协调者), 不需要在 issue #8 评论.
