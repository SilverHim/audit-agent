## 讲解

### 业务背景

- R75 让新程序与新机制按功能名开启. 但配置项 FEATURES 改了以后, 在途项目若照常恢复, 会出两种问题:
  - 项目在另一套程序包与主图上继续, 走到不同的节点.
  - 新闸门出现在项目已经走过的位置.
- 所以项目启动时把功能集冻结进版本快照 (同 R32 冻结程序库 commit 与模型). 之后进程的功能集与之不同时, 这个项目一律不动, 等换回原来的功能集.

### 冻结与比对

- `features_text(features)`: 功能名排序后以逗号连接. 基线为 "critic", 全关为空串.
- `freeze_versions` 写入 `version_snapshot["features"]`. start 与 "没有检查点时以初始状态推进" 共用这一处. 已有快照的项目不覆盖 (R32 的规则不变).
- `features_mismatch(deps, engagement)`:
  - 项目还没有版本快照 (尚未启动) 时为 None, 不比较.
  - 快照没有 features 键 (本条之前建的项目) 时按 "critic" 处理, 所以 main 上已建的项目照常恢复.
  - 与当前进程的 `AgentDeps.features` 相同时为 None.
  - 不同时返回 "项目冻结 critic, 当前 critic,journals". 空集写作 "(空)", 免得出现 "项目冻结 , 当前 critic".

### recover 与 resume (`_proceed`)

- 顺序:
  1. 读检查点与项目.
  2. 已结束的项目 (有检查点且 next 与待执行任务都为空) 照旧不动. 归档项目不因功能集不同而报错, 免得每次启动都给已结束的项目记一条错误.
  3. 功能集不同: run_error 记 `FEATURES_MISMATCH: 项目冻结 ..., 当前 ...`, 释放项目锁, 返回. 不以初始状态推进 (快照已冻结而没有检查点时), 不补做, 不调 ainvoke.
  4. 其余同原规则: 没有检查点时以初始状态推进; 补做; 停在闸门或等人时不动; 否则继续.
- 功能集比对放在补做之前: 补做也会以闸门节点身份写检查点, 同样不能在另一套主图上做.
- resume (POST /resume) 走同一条路, 所以同样不推进, 只记 run_error.

### 决定提交 (`_deciding`)

- 校验顺序 (接口文档第 7 节校验表): ENGAGEMENT_LOCKED → ENGAGEMENT_BUSY → FEATURES_MISMATCH → RESUME_REQUIRED → 其余.
- 比对用取锁后重读的项目. 不同时抛 `DecisionRejected("FEATURES_MISMATCH", "项目冻结 ..., 当前 ...")`, 外壳释放项目锁. 这时还没有写 Store, 也没有读写检查点.
- 闸门决定, 复核决定与更新客户资料都经 `_deciding`, 所以都拒绝.
- 经 HTTP 为 409, 响应体 `{"code": "FEATURES_MISMATCH", "message": "项目冻结 critic, 当前 critic,journals"}`.

### 总览提示

- 总览的 run_error 取 runner 记的错误, 所以 recover 之后显示 FEATURES_MISMATCH.
- 前端横幅标题改为 "功能开关与本项目启动时不同，项目已暂停推进。请把 FEATURES 改回项目启动时的设置并重启应用。" (英文同义), 不显示 "继续执行" 按钮.
- 提交决定被拒时, 前端照常用 `apiMessage` 显示 "FEATURES_MISMATCH: 项目冻结 ..., 当前 ...".

### 测试

- `tests/test_runner.py::test_start_freezes_version_snapshot` (验收 1): 快照键加 features, 值为 "critic"; 其余断言不变.
- `test_mismatched_features_do_not_advance` (验收 3): 基线启动, 停在 ACC-01. 再用同一检查点与存储, 建 {critic, journals} 的 runner (程序库, 依赖, 主图都按它重建):
  - recover: ainvoke 被换成记录调用的替身, 调用为 0; 不持锁, 没有后台任务.
  - run_error 为 "FEATURES_MISMATCH: 项目冻结 critic, 当前 critic,journals".
  - 提交 ACC-01 approve: DecisionRejected, code 与消息逐字相符, 项目锁已释放.
  - 经 HTTP: POST gate-decisions 为 409, code 为 FEATURES_MISMATCH; GET 总览的 run_error 以 FEATURES_MISMATCH 开头.
  - resume 同样不推进.
  - 检查点的值, 下一步, 历史条数, Store 行数与 recover 之前相同.
  - 换回基线 runner: recover 无错误, 不推进 (停在闸门); 提交 ACC-01 approve 后走到 gate_p1_risk.
- `test_legacy_snapshot_counts_as_baseline` (验收 2):
  - 快照没有 features 键: 基线下不报; {critic, journals} 与空集分别报 "当前 critic,journals" 与 "当前 (空)".
  - 没有快照的项目不比较.
  - 带旧快照, 没有检查点的项目用基线 runner recover, 照常走到 ACC-01.
- `test_check_order_around_features_mismatch` (验收 4):
  - Store 中放一个检查点里没有的决定. 功能集不同的 runner 报 FEATURES_MISMATCH, 功能集相同的报 RESUME_REQUIRED.
  - 先取项目锁时报 ENGAGEMENT_BUSY.
  - 项目锁定后报 ENGAGEMENT_LOCKED.
  - 每次被拒后项目锁都已释放.
- `test_frozen_project_without_checkpoint_is_not_started`: 快照已冻结而没有检查点. 换功能集后 recover 不建检查点, 也不写固定集; 换回基线后推进到 ACC-01.
- `test_store_ahead_is_not_caught_up_under_other_features`: Store 有检查点里没有的 ACC-01 决定.
  - 换功能集后 recover 不补做, 检查点, Store 与留痕条数都不变; 总览显示 FEATURES_MISMATCH.
  - 换回基线后补做, 走到 gate_p1_risk.
- `test_ended_project_is_not_flagged`: 拒绝承接后到 END 的项目, 换功能集后 recover 不记错误.
- `test_profile_update_and_review_record_rejected`: 更新客户资料与复核决定都报 FEATURES_MISMATCH, 项目锁已释放, 检查点, Store 与画像版本不变.
- 变异: 去掉 `_proceed` 或 `_deciding` 中的比对, 相应用例都失败.
- Numbat 回归 (验收 5): 同一进程, 同一功能集. R55 至 R57 与连库全流程照常通过.
