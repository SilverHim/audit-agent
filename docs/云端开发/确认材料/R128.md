来由: JR-51. verify_G2 JR-11 (major): "管理层没有申报" 是 GEN-03、GEN-01 结论的核心事实, 现有指针来源无处可指. 取其方案 (a), 新增指针来源.

规模 S, 档位 high. 协调者指示直接做, 有要拍板的点停下来问. 做下来没有遇到要拍板的点; 下面 "讲解" 里写了几处按范围自行定的做法.

## 改动摘要

- 契约:
  - `contracts/models.py`: PointerSource 加 `client_profile`; EvidencePointer 的 source_id 与 locator 注释写明客户画像的写法.
  - `contracts/services.py`: JudgmentContext 与 ValidationContext 各加 `client_profile: ClientProfile | None = None`.
- `services/judgment_engine.py`:
  - PointerResolver 加 profile 参数 (取 ValidationContext.client_profile). client_profile 指针按以下规则解析, 都不通过时该步 unsupported, 规则同行指针:
    - 上下文没有画像: "校验上下文没有客户画像";
    - source_id 须等于画像 ID, 否则 "不是本项目采用的客户画像 …";
    - locator 须是 ClientProfile 的顶层字段名, 否则 "… 不是客户画像的字段".
  - 通过的改写为 voucher, internal_copy (管理层申报, 不采信模型填的值).
  - 判断草稿与独立复核的校验都用上下文中的画像; judge 把 JudgmentContext.client_profile 放进 ValidationContext.
  - evidence_key (独立复核的证据白名单与争议呈递的去重) 对画像按 (来源, ID, 字段) 比对 (第 1 轮修改).
- `agents/review.py` (GEN-09):
  - 新方法 cited_profile: 判断引用了 client_profile 时, 读本项目采用的那一版 (状态中的 client_profile_version, 经 ingest.client_profile); 没引用时为空, 不读项目存储. collab 打开时 review 在触发判定前取, 交给 cross_check; 关闭时命中触发规则后由 cross_check 取 (第 1 轮修改).
  - given_evidence 按它解析; evidence_content 给出该字段的 JSON; 第一轮的 ValidationContext 也带上它, 复核方引用同一指针的步骤才解析得了.
- 前端: `bun run generate-client`, PointerSource 多一个取值. 证据链接对 client_profile 显示 "{画像 ID} · related parties", 点开是现有的 "无法打开" 说明 (不在本条范围, 见讲解).
- 接口文档:
  - 第 2.2 节: PointerSource, EvidencePointer 的注释.
  - 第 5 节:
    - JudgmentContext, ValidationContext 的新字段;
    - OutputValidator 引用级表格里 client_profile 的解析规则, 以及证据种类与可靠性的说明;
    - GEN-09 第一轮的证据内容与 cited_profile.
- 测试 (第 1 轮修改后):
  - `tests/test_output_validator.py`: test_client_profile_pointer_resolves_only_against_the_context, 4 例, 用 Xero 演示画像, 标 external.
  - `tests/test_judgment_engine.py`: test_judge_passes_the_client_profile_to_the_validator, 2 例, 用 Numbat 画像.
  - `tests/test_review_agent.py`:
    - test_cited_client_profile_is_given_from_the_adopted_version, 按功能集 (collab 关与开) 2 例;
    - test_critic_citing_a_profile_field_not_given_is_unsupported;

## 讲解

- **为什么 internal_copy, voucher.** 客户画像是管理层申报的资料 (ASA 550 第 13 段的询问结果), 不经核实, 不是外部证据. 证据种类与内部记录一样用 voucher, 可靠性取范围写的 internal_copy. 功能 collab 下, 只靠画像的判断会命中 GEN-09 的 internal_copy 触发规则. 这与 "只靠内部复印件" 的本意一致.
- **为什么 locator 认全部顶层字段 (含 id, version).** 验收写的是 "ClientProfile 的顶层字段名", 照字面取 `ClientProfile.model_fields`. 不认嵌套路径 (如 related_parties.0.name), 嵌套路径按 "不是客户画像的字段" 处理.
- **解析不读项目存储.** OutputValidator 本来就没有项目存储依赖 (构造参数只有财务存储, 程序库, 留痕), client_profile 只能取自上下文. 读哪一版由放进上下文的一方决定:
  - A6 的判断: 由调用方填 JudgmentContext.client_profile. 现有程序 (REV-02, REV-03, CSH-02) 不填, 行为不变.
  - GEN-09: 由 A7 按状态中的版本读.
- **GEN-09 只在引用了画像时读存储.** 现有判断都不引用画像, 复核流程不多读一次存储. collab 关闭时触发判定用不到证据, 命中触发规则之后才读; collab 打开时触发判定要看第一轮证据 (internal_copy), 先读.
- **复核方只能引用第一轮给过的字段.** 第一轮只给判断所引字段的 JSON, 所以独立复核的白名单对画像比到字段 (evidence_key), 与文件比到页同理.
- **前端没有专门的画像证据视图.** 范围不含前端. 证据链接已有兜底: 标签显示画像 ID 与字段名, 点开显示无法打开的说明. 弹窗显示画像字段已另立 R302.

## 验收

1. 指针 {client_profile, CLIENT-XERO-3C1332BB-Q1, related_parties}: test_client_profile_pointer_resolves_only_against_the_context.
   - 上下文为该画像时解析通过, 改写为 voucher, internal_copy (模型填的是 external, external_original).
   - locator 不是顶层字段, source_id 是 CLIENT-001, 上下文没有画像: 三种情况都是该步 unsupported, 错误各写原因, 指针原样保留.
2. 解析不读 EngagementStore, 只认上下文中的版本:
   - 校验器没有项目存储 (make_validator 只给财务存储, 程序库, 留痕).

   - GEN-09 的版本: test_cited_client_profile_is_given_from_the_adopted_version 中, 项目存储有 v1 与改出的 v2 (多一个关联方), 状态采用 v1. 第一轮只给 v1 的关联方, 没有 v2 新加的.

4. 现有指针来源与 Numbat 回归不变:
   - 现有判断与抽取的调用方都不填画像, 解析路径只多一个分支.
   - test_output_validator (R33 的各条), test_review_agent, test_judgment_engine 与默认全套通过 (见环境限制).
