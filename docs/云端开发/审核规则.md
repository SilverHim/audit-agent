# 审核规则 (云端版)

本地开发时每条需求由 Codex 只读审核. 云端用不了 Codex, 改由一个**独立的只读审核子代理**按本规则审核. 实现由开发代理写, 审核子代理只审不改仓库.

## 分级 (10-20 用户定: 按大小与风险分级, 小需求打包)

- **免审**: 规模 S, 且不改 `contracts/`, 迁移, `orchestration/`, `persistence/`; 或只改文档, 测试, mock fixture, 准则片段 (逐字测试自带守卫), 前端文案. 协调者读增量并跑检查后直接集成.
- **普审**: 其余档位 high 的需求. 审核子代理读增量与相关代码, 只跑本条相关的测试文件, 不做变异核对.
- **严审**: 档位 xhigh 的需求. 普审之外, 审核子代理在导出副本上做变异核对, 看测试能否区分对错.
- **打包**: 同一模块的几条小需求可以一起开发, 一次送审 (按包里最高的一级审), 仍一条需求一次提交.

## 检查分工 (10-20 起, 全套只跑一次)

- 开发方: 送审前跑全套 (默认全套; 改持久化时加 `-m slow`; 改前端时加前端四项), 结果写进交付消息.
- 审核方: 不重跑全套. 跑 ruff, mypy 与本条相关的测试文件 (新增与改过的测试, 改动模块对应的测试); 改了持久化时只跑本条相关的连库测试文件; 严审另做变异核对. 认为相关范围不够时, 写明理由再扩大.
- 协调者: 见 `开发流程.md` "协调者合入时".

## 怎么调用

- 每条需求写完, 开发方的全套检查 (见 "检查分工") 全绿后再送审.
- 开发代理写好本轮提示 (需求编号, 改了哪些文件, 每处改动的意图, 值得重点看的地方; 第 2 轮起加上修改说明与对未采纳意见的理由), 用子代理工具启动审核子代理, 模型用 opus, 把本文件路径, 需求清单中该需求的小节, 本轮增量 (`git diff` 相对上一条需求的提交) 与提示一并交给它.
- 审核子代理只许读文件, 跑检查与自己写的探针测试 (探针写在临时目录, 不进仓库); 不许改仓库文件.
- 输出按 `审核输出格式.json` 的结构, 全部中文.

## 审什么

1. 正确性: 逻辑错误, 边界情况, 异常路径, 并发, 重放 (ID 确定性, 幂等, 版本号).
2. 需求: 是否满足该需求的全部验收标准; 有没有做多或做少.
3. 契约: 与 `docs/开发接口文档.md` 的签名, 字段, 错误码, ID 规则是否一致; 改了 `src/backend/contracts/` 是否在同一次提交里同步改了接口文档.
4. 测试: 新行为是否都有测试; 测试数据能否区分对错 (有优先级或多个来源的规则, 测试数据须互不相同). 有疑点时写探针测试验证, 在结论里给出探针路径.
   测试质量 (按 `开发提示词.md` "写测试" 一节): 有没有只测文档措辞的, 为一两个断言重跑全流程的, 复制粘贴的重复用例, 说不出防什么的守卫; 用 `uv run pytest --durations=20` 看本条新增用例的耗时. 发现即 minor, 让默认测试明显变慢或整段重复的记 major.
5. 约定: `CLAUDE.md` 列出的约定, 如 Python 注释与 docstring 用中文半角标点.
6. 数据规则: 不得改原始数据 (Xero 快照, Numbat 数据集); 补造文件标明合成; 注入错误只在测试的临时副本里; 不得在任何文件里写出 Xero 登录账号联系人的真实姓名与邮箱.

不审: 纯风格偏好; 与本需求无关的旧代码 (看到严重问题可以 minor 提一句).

## 严重度

- blocker: 结果错误, 数据损坏, 测试或检查失败
- major: 漏了验收标准, 与接口文档不一致, 关键路径没有测试
- minor: 不影响正确性, 但应该改
- nit: 可改可不改

`passed` 为真当且仅当没有未解决的 blocker 与 major.

## 多轮

最多 3 轮. 第 2 轮起, 审核子代理在 `previous_findings` 里逐条给上一轮问题的状态: `fixed`, `not_fixed`, `withdrawn` (接受对方理由撤回); 新问题列在 `findings`, 编号不与旧的重复. 3 轮后仍有分歧的意见, 协调者连同双方理由用白话选择题交用户裁决, 结论写进需求清单该条的注.

审核子代理的结论是参考, 不是命令: 开发代理逐条核实, 认同的改, 认为误报的写理由.
