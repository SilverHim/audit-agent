# R312 确认材料: 真实模型走通暴露的输出截断与指针问题

## 改动摘要

- `adapters/llm.py`, LiveLLMClient 的截断处理:
  - 读 `choices[0].finish_reason`. 为 length 时, error 写成截断说明 `TRUNCATED` (英文, 写明上限), raw 照常保留.
  - 服务端因输出达到上限回 400 时不再抛错 (`output_limit_reached` 认错误信息里的 "output limit was reached"). 返回 raw 为空, token 记 0, error 同上.
  - 两种截断都由校验按语法失败, 把这句话回传给模型重试.
- `contracts/knowledge.py`: `LLMSpec.max_tokens` 缺省 4096 改为 32768.
- `adapters/llm.py`: LiveLLMClient 单次请求超时缺省 120 秒改为 600 秒 (`TIMEOUT`).
- `services/judgment_engine.py`: 判断改用 `JUDGMENT_SYSTEM`, 多写一句: 规则例外不是证据来源, 不把例外 ID 写进指针, 改引例外所指的行.
- 接口文档: 第 4 节 LiveLLMClient, 第 5 节调大模型的请求, 第 8 节 LLMSpec.
- 用例:
  - `test_llm_live`: finish_reason 三种; 输出达上限的 400.
  - `test_llm_call`: 截断后的重试请求 (两种截断); 缺省上限的两处断言改为 32768.
  - `test_judgment_engine`: 把例外 ID 当留痕引用的指针.

## 复现与来由

验收 1. 协调者用密钥跑 scratchpad/r312/repro_gen02.py (不入库), 在主检出 0fe606b. 对象 XJ-397, 提示 24645 字符, prompt 6203 token.

| 上限 | finish_reason | completion | 其中推理 | 正文 |
|---:|---|---:|---:|---:|
| 4096 | length | 4096 | 4096 | 0 字符 |
| 16384 | stop | 5764 | 2235 | 13740 字符 |

截断推断成立: 推理 token 把上限用光, 正文为空. 放宽上限后能给出完整输出.

验收 4, 5. 协调者查了 audit_int 的 ENG-2026-1130:
- **对象为空的 GEN-02 failed 任务**:
  - RUN-GEN-02-1 失败, 原因 "LLMTransportError: HTTP 400 ... max_tokens or model output limit was reached".
  - JSON 模式下输出不完整时, 服务端回的是 400; 传输层按不可重试抛错, 整次执行就失败了.
  - 这是缺陷, 已随验收 2 修: 这种 400 改为截断的响应, 照常回传重试.
- **trail 指针**:
  - J-CSH-02-1-BA-091 v1 (A6 写) 的 evidence 与推理链都有 trail X-CSH-02-1-D04-1; v2 (A1 争议裁决后的新版) 原样带着.
  - 这条路径有引用级校验. 按现行设计, 解析不了的指针标 unsupported 并原样保留 (接口文档第 5 节).
  - BA-091 的争议任务也由此而来: 有 unsupported 步骤, 触发了 A7.
  - 根因: 规则例外没有对应的指针类型, 提示词也没说怎么引.

## 方案取舍

- **截断 (验收 3)**: 缺省上限提高到 32768 (协调者定), 截断说明回传给模型.
  - 实测 XJ-397: 一次推理超过 4096; 另一次推理 2235 加正文约 3500, 共 5764. 32768 留足余量.
  - 上限只封顶, 不增加实际用量. 最坏一次输出约 0.016 美元.
  - 不做 "重试时加倍上限": 要在响应里另加截断标志, 得改契约; 上限提高后截断已经少见.
  - 截断说明走语法级错误回传, 不另开一套重试.
- **认 400 的办法**: 只能按错误信息的字样认, 因为 error.param 与 code 都为空, 没有别的信号. 只认这一句, 其余 400 照旧抛错.
- **指针 (验收 4)**: 不改引用级 (现行设计, 有用例), 不新增指针类型.
  - 改在判断的系统提示词里写一句. 只改一处, 全部判断程序 (含以后新增的) 都受用.
  - 不在六份带规则例外的提示词里各写一遍.
- **显式写了上限的模板不改**: DOC-CLASSIFY 512, GEN-09 第二轮 1024, DOC-REGISTRY 2048, DOC-SHEET 4096, DOC-STATEMENTS 8192.
  - R311 首跑里, 跑到的几个都一次通过; 以后再截断也会回传说明.
  - DOC-SHEET 首跑没跑到. 它的上限与旧缺省相同, 真实模型下仍可能截断.
- **超时与上限配套**: 缺省超时从 120 秒放宽到 600 秒, 不按请求的上限另算 (最简).
  - 请求不是流式, 模型写完之前收不到字节, 读超时就是整次生成的时间.
  - 120 秒对 32768 token 来说, 每秒要写约 270 token 才来得及; 600 秒只要每秒约 55 token.
  - 代价: 超时会走传输层重试 3 次, 最坏一次调用要等约 40 分钟. 测试连接另有 20 秒的超时, 不变.

## 验收对照

1. 复现: 见上表.
2. finish_reason: length 时 error 为截断说明, stop 与缺失时照旧为解析错误, raw 都保留 (`test_truncated_output_says_so`). 输出达上限的 400 不抛错, 只发一次 (`test_output_limit_400_is_a_truncated_reply`).
3. 两种截断后都重试. 第二次请求的上限为 32768, 末条消息含截断说明, 第二次通过 (`test_truncated_reply_is_retried_with_the_note`).
4. 判断路径收到例外 ID 当留痕的指针: 所在步骤 unsupported, 指针保留, 判断照常得出; 请求的系统提示词含新写的那句 (`test_finding_cited_as_a_pointer_marks_its_step`).
5. 来由见上, 随验收 2 修了.
6. 现有用例见下. R311 真实模型重跑由协调者用密钥跑.
